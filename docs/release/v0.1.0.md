## 一句话定位

**FlowGate 是给 DeepSeek Harness 加「硬约束开发流程」的插件**：把「澄清 → 上下文 → 设计拆解 → TDD 执行 → 验证 → 交付」做成 7 阶段状态机 + 46 项门禁检查 + 宿主层写操作守卫，让模型不能跳步、不能越界、不能拿自述当证据；所有判断由宿主代码执行，而不是提示词。

## 这个版本带来什么

- **7 阶段硬约束流水线**（S0–S6）+ 复杂度（低/中/高/超高）× 风险（普通/高）等级矩阵；低复杂度可以走只做 2 次人工确认的快车道。
- **三道硬约束**：顺序（S0–S3 写源码一律拒绝，S4 只能写当前任务卡范围）、证据（插件执行验证并签发带输入哈希的回执，改动后回执过期）、交付（G1 / G3 / G6 人工门，模型没有批准/放行/降级工具）。
- **可解释的拦截**：每条规则给出规则 id、触发事实、未来路径和单次放行方式；`/flow allow-once`、例外、`/flow off`、`/flow repair` 与误判反馈闭环，不会把人锁死。
- **跨会话状态**：`.flowgate/` 目录 + 哈希链账本（HMAC 防篡改）+ 会话租约；换会话自动接续，交接摘要注入。
- **一组 `flow_*` 模型工具（共 15 个，含派发模式的 `flow_dispatch_next`）**：`flow_status`、`flow_submit`、`flow_task_start`、`flow_verify`、`flow_task_done`、`flow_dispatch_next` 等；tools 模块自身注册 14 个（`/flow doctor` 显示 14/14），派发工具由派发模块单独注册。人工专属动作不暴露给模型。
- **可视与交付物**：输入框状态条、右侧栏 8 视图面板、单文件 HTML 交付报告、跨会话看板、M-1～M-18 指标导出。
- **开箱可学的内容**：15 个内置技能（`SKILL.md` + `learn.md`）、3 个可独立构建和测试的基准仓库（TypeScript / Python / Java），以及中文/英文文档。
- **对宿主侵入小**：npm 包不含 `@deepseek-ai/*`（只作可选 peerDependencies）；插件故障不阻塞宿主启动；不联网、不上传代码、无遥测。

## 安装（隔离 profile）

发布前的开发验证、以及首次安装，都建议用**隔离 profile**，不要装进日常 `desktop` profile：

```bash
# 用桌面端自带 CLI（全局 dsh 可能是旧版，不要用）
DSH="/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh"

# 1. 从官方 web 模板建隔离 profile（只需第一次；重复执行会覆盖该 profile）
"$DSH" flowgate-dev --from-default-profile web

# 2. 从 npm 安装本版本（发布后）
"$DSH" plugin --profile flowgate-dev add dsh-flowgate@0.1.0

#    开发中也可以直接 link 源码仓库（需先在仓库里 pnpm install && pnpm build）：
#    "$DSH" plugin --profile flowgate-dev add link:/path/to/dsh-flowgate

# 3. 确认组合树的插件行（应包含 dsh-flowgate 与预设 preset-flowgate*）
"$DSH" --profile flowgate-dev --dump-config | grep -i flowgate

# 4. 启动 Web 宿主
"$DSH" --profile flowgate-dev
```

> `dsh plugin` 会把参数原样转给 profile 目录里的 pnpm，因此也可以用 `remove dsh-flowgate` 卸载或 `add dsh-flowgate@<版本>` 固定版本。
> Windows / Linux 用户的 DSH CLI 路径不同，使用本机桌面端安装位置下的 `runtime/cli/bin/dsh` 即可。

**确认装好了**：在受管控的项目里执行 `/flow doctor`，应看到插件版本、项目根、账本、守卫心跳、工具覆盖、宿主能力（✓/✗）与降级说明；`/flow init` 之前不会拦截任何操作。

## 快速开始

```text
/flow init                        # 扫描仓库，生成 .flowgate/project.md 草稿（负责人确认）

/flow approve G1                  # 负责人定稿需求

```

## 已知缺口

如实列出，完整版与后续动作见 [implementation-status.md §4](../impl/implementation-status.md) 与 [CHANGELOG.md](../../CHANGELOG.md)：

- 有 / 无插件对照评测（M6 / T6.1）**未执行**，暂无 M-15 / M-18 实测数字。
- 三个 agent preset 的真实会话切换验证未完成；精简组合可能跳过 preset 行（不影响 `/flow`、工具与守卫）。
- 浏览器内人工交互（面板按钮的 Remote 兜底、低复杂度确认卡）未走查。
- 审查 / 派发 / 并行 worktree 的完整真机验证依赖提供 subagents 的宿主组合；当前精简 web 组合按降级处理。
- `appendPluginRecord` 属实验性 API，DSH 升级可能失效；每个 RC 需跑 `verify:compat`。
- 核心逻辑分支覆盖率 67.8%（2026-10-31 重测），低于 80% 目标；host 层不在 vitest coverage 口径内。

## 升级与回滚

- **升级（后续版本）**：`dsh plugin --profile <profile> add dsh-flowgate@<新版本>` 覆盖安装即可；升级后执行 `/flow doctor` 与 `/flow repair` 自检。项目数据全部在项目根 `.flowgate/`，与插件安装位置无关；v0.1.0 是首个版本，暂无状态迁移步骤。
- **回滚插件**：`dsh plugin --profile <profile> add dsh-flowgate@<旧版本>` 固定回旧版本；或 `dsh plugin --profile <profile> remove dsh-flowgate` 卸载。插件缺失时项目不会被 FlowGate 拦截，`.flowgate/` 记录原样保留。
- **回滚项目状态**：FlowGate 不修改项目源码之外的文件；`.flowgate/` 默认不进 git。若需彻底清除门禁状态，删除项目根 `.flowgate/` 即可（会丢失全部流程记录）；账本异常时先试 `/flow repair`。
- **npm 包本身**：已发布版本不做撤回（unpublish），有问题发补丁版本。

## 发布前检查清单（负责人内部）

> 本 workflow 设计为「凭据就绪后，推 tag 即发布」。以下每一项都需要人工确认。

1. **版本与 tag 决策（必须）**
   - 方案 A：保持 `0.1.0`，把 `v0.1.0` tag 前移到发布提交（`git tag -f v0.1.0 <commit>` + `git push -f origin v0.1.0`）。公开仓库改写已有 tag 有风险——旧 tag 指向 `f53d5f1`，需确认没人基于它构建。
   - 方案 B：保留旧 tag 历史，`package.json` bump 到 `0.1.1` 后打新 tag（需同步更新本文件名为 `docs/release/v0.1.1.md`，workflow 按 tag 名找说明文件）。
   - 无论哪种方案：tag 指向的提交必须在 `origin/main` 上、CI 绿，且 `package.json` 版本 == tag 去掉 `v` 后的版本（workflow 会强制校验）。
2. **npm 凭据**：仓库 Settings → Secrets and variables → Actions 添加 repository secret **`NODE_AUTH_TOKEN`**（不是 `NPM_TOKEN`；本 workflow 只读前者）。值为 npm granular access token，需 Packages/Publish 权限，并勾选允许 bypass 2FA。`GITHUB_TOKEN` 由 Actions 自动提供，用于创建 Release。token 不写入仓库、不打印到日志。
3. **npm 包名与权限**：`npm view dsh-flowgate` 当前 404，包名可用；首次发布由 `npm publish --provenance --access public` 完成（Node 22 / npm 10，仓库公开，OIDC 由 `id-token: write` 提供）。若 `dsh-flowgate` 已被占用，需要先改名并同步 `package.json` 的 name、client loader 的模块 id、`cordis.patch.yml` 与文档中的引用。
4. **可选元数据**：`package.json` 目前没有 `repository` / `homepage` / `bugs` 字段。不影响发布与 provenance 生成，但建议补上（npm 页面会显示源码链接）。`package.json` 的 `files` 不含 `CHANGELOG.md`；如需让 npm 包携带 CHANGELOG 再决定是否加入。
5. **发布前刷新事实**：若在发布前合入新提交（例如补测、评测脚本），请重跑 `pnpm test` 并更新本文与 `CHANGELOG.md` 中的测试数字与 CI 状态，再重新打 tag。
6. **可选人工审批**：可在仓库 Settings → Environments 建 `npm-release`，并给 workflow 的 publish 步骤加 `environment: npm-release` 以启用发布前人工审批（当前 workflow 未预置，避免误建环境）。
7. **提交并推送 workflow**：`.github/workflows/release.yml` 必须先合入 `main` 并推送——`push` tag 事件执行的是 **tag 所指向提交里**的 workflow 文件。
8. **触发发布**：`git push origin main && git push origin v0.1.0`（只推目标 tag，不要 `git push --tags`，避免把其他本地 tag 一起推上去）。workflow 会先做前置校验（凭据 / 版本一致 / tag 在 main 上 / npm 上无同版本 / 无同名 Release），再跑完整 CI，最后 npm publish + 创建 GitHub Release。
9. **发布后验证**：
   - `npm view dsh-flowgate version` → `0.1.0`（registry 传播可能有延迟）；
   - GitHub Releases 页面出现 `v0.1.0`，正文与本文一致；
   - 在干净隔离 profile 里 `dsh plugin ... add dsh-flowgate@0.1.0`，启动后 `/flow doctor` 正常、`/flow init` 可初始化示例项目。
10. **失败恢复**：若 npm 已发布成功但 GitHub Release 创建失败，不要重跑整个 workflow（npm 会因版本已存在而失败）。在本机已 `gh auth login` 的前提下手动补：`gh release create v0.1.0 --verify-tag --title "FlowGate v0.1.0" --notes-file docs/release/v0.1.0.md`。若前置校验或 CI 步骤失败（此时尚未产生任何 npm 发布），修复后可在 Actions 里 Re-run 该次运行，或删除/重推 tag。

## English summary

FlowGate v0.1.0 is the first release of a hard-constraint development-process gate plugin for DeepSeek Harness (DSH 0.2.1-rc.5): a seven-stage pipeline (S0–S6) with 46 gate checks, host-level guard rules for write ordering and task scope, verifier-issued evidence with input hashes, human-only approval gates, cross-session state with a hash-chained ledger, 15 model tools, 15 built-in skills, and a web status bar/panel.

- **Install** (after publishing): create an isolated DSH profile (`dsh flowgate-dev --from-default-profile web`), then `dsh plugin --profile flowgate-dev add dsh-flowgate@0.1.0`.
- **Status**: not yet published to npm; no GitHub Release yet; `v0.1.0` tag currently points to `f53d5f1` (4 commits behind HEAD `e1aef8d`).
- **Verified at HEAD**: 63 test files / 944 tests, CI green, 7/7 DSH compat checks, real web-host walkthrough, and a real-model end-to-end S0→S6 delivery on `ts-todo-api` including a real guard denial.
- **Known gaps**: comparative evaluation not run, preset switching not fully validated, browser-only manual interactions not walked through, experimental `appendPluginRecord` API.
