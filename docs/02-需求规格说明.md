# 02 需求规格说明（PRD）

> 历史方案快照（2026-10-30 定稿）。当前实现状态、已知缺口与验证证据见 [implementation-status.md](impl/implementation-status.md) 与 [release/v0.1.0.md](release/v0.1.0.md)。

> 编号规则：功能需求 `FR-x.y`，非功能需求 `NFR-x`，指标 `M-x`。优先级：**P0** = v0.5（第 6 周的可自用最小版本）必须有；**P1** = v1.0 必须有；**P2** = v1.0 可选。
> 验收场景统一用 GIVEN / WHEN / THEN 写法，这也是 FlowGate 要求 agent 使用的写法。

---

## 1. 背景与要解决的问题

### 1.1 vibe coding 里 agent 的典型失控

- **需求没澄清就开写**：拿到"加个会员续费"就直接写接口，失败处理、幂等、优惠叠加规则都没想（三件套文章里的例子）。
- **跳步**：Claude Code 用户在 [claude-code#69500](https://github.com/anthropics/claude-code/issues/69500) 里的原话是 agent "executes a defined process OUT OF ORDER… skipped Step 0… made code edits"，并要求"block the later action and surface the missing prerequisite"。
- **越界**：顺手重构、重复造轮子、悄悄改变原有行为。
- **"看起来完成了"**：没跑测试，或者拿旧的测试结果宣布完成。
- **风险操作不找人**：加依赖、改迁移、动鉴权和支付、写入密钥。

### 1.2 为什么现有方案不够

| 方案 | 问题 |
|---|---|
| 提示词 / 技能包 | 会被跳过。Superpowers 官方测到改版前 24/24 次跳过设计文档 |
| DSH 计划模式 | 只是引导，"每个工具仍可调用" |
| 现有 DSH 门禁插件 | 默认只提醒；误伤多（`dsh-perm-gate` 3 个用户 issue 全是误判）；静默失效（`dsh-auto-review` 工具名不匹配时无任何告警）；安装后宿主起不来（同一问题复发三次）；面板只展示状态、不能处置；没有"顺序状态机" |

### 1.3 机会

**顺序不可跳过的状态机 + 可解释的拦截 + 能直接处置的面板 + 可学习的可视化 + 自动量化指标。**

## 2. 定位与目标

### 2.1 定位

FlowGate 是一个 DSH 插件：在宿主层用代码强制执行 7 阶段开发流程（规格层 → 执行纪律层 → 交付闭环层），把每一步可视化成能看懂、能回放、能度量的过程。

### 2.2 目标（按优先级）

| # | 目标 | 衡量方式 |
|---|---|---|
| G-1 自用 | 你在 DSH 里做的每个非平凡改动都按流程走，跳不过去 | 实际跳步数（M-2）= 0；交付时越界残留（M-3）= 0 |
| G-2 学习 | 每一步都能看懂在做什么、为什么、合格标准是什么；一次变更结束后能回放全过程 | 7 个阶段都有阶段卡；每次交付生成 HTML 报告 |
| G-3 量化 | 自动统计流程合规、拦截质量、需求质量、验证质量、人工负担和成本 | M-1 ~ M-18 自动计算并可导出 |
| G-4 作品 | 开源发布，可演示、可复现，能在面试中讲清楚 | README、demo、评测报告（9 个基准任务的对照数据） |

### 2.3 非目标

- 不做团队多角色、多仓库、外部需求系统（禅道 / TAPD / Jira）集成。
- 不做内核级沙箱或权限系统（交给 DSH 自己的沙箱）。
- 不替代 DSH 的计划模式、目标、待办，只在其上加门禁。
- 只支持 DSH，不适配其他 agent 宿主。
- 不做自动合并到主干、自动部署。
- 不依赖 OpenSpec、Superpowers、gstack 的任何运行时。

## 3. 角色与场景

### 3.1 角色

| 角色 | 职责 | 不能做什么 |
|---|---|---|
| 负责人（你） | 提需求、回答澄清问题、批准 G1 / G3 / G6、处理风险接管、范围变更和单次放行 | — |
| 主 agent | 在门禁内完成各阶段工作，调用 FlowGate 工具提交产物和证据；S4 派发模式下只负责按执行图调度 | 不能批准任何门、不能放行、不能降低复杂度或风险、不能写插件状态、不能改变执行图的顺序 |
| 执行子 agent（派发模式） | 只拿到一个任务的任务卡、场景和相关上下文；在任务范围内写代码、跑验证，完成后向主会话回传摘要；并行批次里在自己的 worktree 中工作 | 不能写任务范围外的文件、不能调用 `ask_user_question`、不能批准任何门 |
| 审查子 agent | 独立上下文、只读，按规格和代码质量审查；必须读完全部待审内容 | 不能写文件、不能执行命令、不能调用 `ask_user_question` |
| 调查子 agent（只读） | 只回答一个具体问题，回传带源码引用的报告 | 不能写文件、不能执行命令、不能调用 `ask_user_question` |
| FlowGate 插件 | 判定、记录、展示、计算指标 | 从不替人批准 |

### 3.2 典型场景

| 场景 | 复杂度 / 风险 | 流程要点 |
|---|---|---|
| A 新功能："给会员系统加续费功能" | 中或高 / 普通 | 完整 7 阶段；S1 问清续费起算点、幂等、失败补偿、优惠叠加；跨模块时为高复杂度，要写设计和执行计划 |
| B 修 bug："续费后到期日算错了" | 中 / 普通 | S1 以"复现步骤 + 期望行为"为主；S3 通常是"先写复现测试，再修复"两个任务 |
| C 小改动："改按钮文案" | 低 / 普通 | S1 只写目标和验收场景；S2 自动完成（用项目级上下文、跑基线），不写设计和风险登记；G1 与 G3 合成一张方案确认卡，加上 G6 一共 2 次确认；仍要求验证 |
| D 小而危险："改支付回调验签里的一处判断" | 低 / 高风险 | 流程仍然很短（不写设计、一张任务卡、方案确认卡），但风险项逐项确认、必须有回滚方案、TDD 必需、两轮审查加安全审查、运行证据必需 |
| E 需求中途变化：S4 发现漏了"已过期会员续费"的规则 | 原等级 | 回到 S1 写增量规格，重新过 G1；已完成任务不受影响，新增任务过 G3 |
| F 从 0 开发："做一个会员管理系统" | 每个变更各自评估 | 先做项目级澄清，产出路线图并由负责人批准（GR）；第一个变更是工程骨架；之后按能力逐个变更推进，每个变更照常走 S1–S6 |
| G 跨会话接续：第一个会话把 T3 做到 RED 后关掉 DSH，第二天开新会话 | 原等级 | 新会话自动附着到这个变更，注入交接摘要和 T3 的任务卡；T3 从 RED 接着做，回执和 TDD 状态都还在 |
| H 可以并行的大功能：续费拆出 3 块互不相关的逻辑 | 高 / 普通 | S3 的执行计划把这 3 块放进一个并行批次；S4 主会话同时派 3 个子 agent，各自在独立 worktree 里开发；集成检查点合并并跑完全量测试后，才进入下一批 |
| I 只想弄清原因："为什么续费后到期日多了一天" | 分析任务 | 只读排查，结论带可核验的源码引用后归档；之后要修复时新建关联变更，直接引用这份结论 |

## 4. 流程模型

### 4.1 阶段与门禁

| 阶段 | 入口条件 | 本阶段 agent 能写什么 | 出口门 | 出口门检查要点 | 放行 |
|---|---|---|---|---|---|
| 项目路线图（仅从 0 开发） | 空仓库，或负责人声明这是新项目 | `.flowgate/project-clarify.md`、`.flowgate/roadmap.md` | GR 路线图批准 | 项目级六要素闭合；能力拆分无遗漏、依赖无环；第一个变更是工程骨架；MVP 切线已标出 | **人工** |
| S0 立项 | 用户提出代码改动需求 | 无 | G0 | 变更已创建、复杂度和风险已建议、契约已冻结 | 自动 |
| S1 需求澄清 | G0 通过 | 本变更的 `clarify.md`、`proposal.md`、增量规格 | G1 需求定稿 | 六要素闭合；每条需求至少一个可测试场景；未决问题为 0 | **人工** |
| S2 上下文 | G1 通过 | 本变更的 `context.md` | G2 | 必填段齐全；测试命令可执行（项目确实没有测试时改用构建、类型检查和 lint）；基线已记录 | 自动 |
| S3 设计拆解 | G2 通过 | 本变更的 `design.md`、`risk.md`、`tasks.md`（含执行计划） | G3 计划批准 | 方案对比；风险五类齐全；任务卡检查通过；追溯全覆盖；执行计划通过并行安全检查 | **人工** |
| S4 执行 | G3 通过 | 当前任务范围内的源码和测试（并行任务在各自的 worktree 里） | G4 | 按执行图完成全部批次：每个任务通过任务门（有效的验证回执、范围、TDD、审查），每个并行批次通过集成检查点 | 自动 |
| S5 验证 | G4 通过 | 只能通过"修复任务"写 | G5 | 全量测试相对基线无回归；无未处理 critical / major；验收场景全覆盖；运行证据（按风险） | 自动 |
| S6 交付 | G5 通过 | `CHANGELOG`、文档 | G6 交付确认 | 交付清单全部满足 | **人工** |

回退路径：S5 失败 → 生成修复任务回到 S4；任意阶段发现需求缺口 → 回到 S1 写增量；人工门被退回 → 留在本阶段，退回意见注入给 agent。

低复杂度的人工门：G1 的检查项照常执行，但不单独等你批准；到 G3 时把 G1 和 G3 的内容合成一张"方案确认卡"（目标、验收场景、要改的文件、验证方式；高风险时加上风险项和回滚方案），你确认一次就同时通过 G1 和 G3。加上 G6，低复杂度一共 2 次确认。

### 4.2 流程等级：复杂度 × 风险

流程等级分两个维度：**复杂度决定流程有多长，风险决定检查有多严**。两者独立组合，例如"低复杂度 · 高风险"。

**复杂度**（走哪些阶段、写哪些产物）：

| 项目 | 低 | 中 | 高 | 超高 |
|---|---|---|---|---|
| 典型需求 | 边界明确的局部修改（改文案、单文件修复） | 常规功能或缺陷修复 | 跨模块、有先后依赖 | 完整新模块或大范围重构 |
| S1 需求澄清 | 精简：目标 + 验收场景 | 六要素 | 六要素 | 六要素 + 失败路径清单 |
| S2 上下文 | 用项目级上下文（不写 `context.md`，自动跑基线） | 项目级 + 本次相关接口与数据 | 同左，接口约束和数据模型必填 | 同左 |
| S3 设计 | 免 | 有多个可行方案时才写 | 必需，含 2–3 个方案对比 | 必需，另写架构边界、影响和取舍 |
| S3 执行计划 | 1 张任务卡 | 顺序批次 | 顺序或并行批次 | 顺序或并行批次；超过 12 个任务就拆成多个变更 |
| 人工确认 | 2 次：方案确认卡（G1 与 G3 合并）、G6 | 3 次：G1、G3、G6 | 3 次 | 3 次 |
| 每任务审查（普通风险时） | 免，S5 终审一次 | 一轮 | 一轮 | 一轮 |
| S6 复盘 | 简版 | 完整 | 完整 | 完整 |

**风险**（检查有多严）：

| 项目 | 普通 | 高风险 |
|---|---|---|
| 典型信号 | 不触及敏感区域 | 鉴权、支付、数据迁移、密钥、基础设施、生产配置、删除受版本控制的文件、公共接口变更 |
| S3 风险登记 | 低复杂度免填（触发器照常生效），其余五类必填 | 五类必填；高风险项在 G3（低复杂度时在方案确认卡上）逐项确认；必须有回滚方案 |
| S4 TDD | 逻辑类任务必需（低复杂度建议） | 全部任务必需，豁免要人批 |
| 审查 | 按复杂度（见上表） | 每个任务两轮（规格符合 → 代码质量），S5 终审加安全审查 |
| S5 运行证据 | 有运行命令时必需 | 必需（日志 + 冒烟） |
| 手工证据 | G6 时汇总确认 | G6 时逐条确认 |

所有等级都要求：S5 全量测试与基线对比无回归、验收场景全部有证据、验证回执由插件执行。

等级规则：

- 插件根据信号（关键词、预计涉及的路径、模块数量、敏感路径触发器）分别建议复杂度和风险并说明理由；负责人在 G1（低复杂度时在方案确认卡上）确认。
- agent 可以申请提高任何一个维度，立即生效；降低只能由负责人用命令执行，并要写理由。
- 风险中途提高时，已完成任务的审查按新标准重新要求，验证回执保留；已经进入 S5、S6 的退回 S4。复杂度中途提高时，回到 S3 补设计和执行计划，已完成且不受影响的任务保留。

## 5. 功能需求

### FR-1 需求理解（S1）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-1.1 | **先挖后问**：提问前先读项目里与需求相关的代码、已有规格和文档，在第一条消息里复述"我理解的需求"和"我在项目里发现的事实" | P0 |
| FR-1.2 | **结构化提问**：用 `ask_user_question` 分轮提问；每轮 ≤ 4 题；每题 2–4 个选项，推荐项放第一个并标注；每题说明"这个回答会改变什么"；允许自定义回答 | P0 |
| FR-1.3 | **六要素闭合**：目标、边界（做 / 不做）、角色与权限、验收标准、约束（非功能）、未知与假设，每个要素都要有结论或被负责人接受为假设 | P0 |
| FR-1.4 | **验收标准可测试**：每条需求至少一个 GIVEN / WHEN / THEN 场景；THEN 里出现未量化的模糊词（快、友好、适当、尽量、等等）时检查失败 | P0 |
| FR-1.5 | **复述确认**：生成 `proposal.md` 和增量规格后，给出一页"最终需求摘要"供负责人确认 | P0 |
| FR-1.6 | **G1 人工定稿**：只能由负责人在面板或用 `/flow approve` 批准；退回时附意见；低复杂度时与 G3 合并为一次确认（见 4.1） | P0 |
| FR-1.7 | **需求变更走增量**：G1 之后修改需求只能写增量（ADDED / MODIFIED / REMOVED），重新过 G1；计入返工指标 | P1 |
| FR-1.8 | **防模板化**：每个问题必须引用已挖到的事实或前面的回答；已能从项目里查到答案的问题不问；问题数和"自定义回答占比"计入指标 | P1 |
| FR-1.9 | **问到为止**：默认最多 4 轮；4 轮后仍未闭合的要素列为"未决问题"，必须由负责人决定或接受为假设，否则 G1 不通过 | P1 |
| FR-1.10 | **事实带引用**：澄清记录里的"已知事实"写成 `文件:起止行` 形式的源码引用，插件核验引用存在并记录哈希；没有引用的内容只能算假设 | P1 |

验收场景：

- GIVEN 用户输入"加个会员续费功能" WHEN 进入 S1 THEN agent 先读取与会员相关的代码和规格，第一轮问题中至少引用一处项目事实。
- GIVEN 某条验收场景的 THEN 写着"续费要快" WHEN 提交 G1 THEN 检查失败，指出"快"未量化，并给出"改为可测量阈值，例如 p95 < 300ms"的提示。
- GIVEN 六要素里"边界·不做"为空 WHEN 提交 G1 THEN 返回缺失项和示例写法。
- GIVEN G1 已通过 WHEN agent 修改 `proposal.md` THEN 写入被拒绝，提示走需求变更（增量）。

### FR-2 任务拆解（S3）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-2.1 | **设计文档**：中复杂度在有多个可行方案时写，高、超高复杂度必需；内容为 2–3 个方案对比、推荐方案和理由、数据流、错误处理；超高复杂度另写架构边界、影响和取舍；高风险必须有回滚方案 | P0 |
| FR-2.2 | **任务卡字段**：id、标题、覆盖的场景、源码范围、测试范围、新文件清单、依赖、TDD 要求、验证命令、风险标签、规模 | P0 |
| FR-2.3 | **任务卡检查**：依赖无环；每个场景至少被一个任务覆盖；每个任务至少覆盖一个场景（或标为 chore 并写理由）；范围不能是整个仓库；规模上限（默认 ≤ 5 个文件、预计 ≤ 200 行改动）；必须有验证命令；一个变更最多 12 个任务，超过必须拆成多个变更；新文件可以写成模块级通配（如 `src/renewal/**`），但必须落在任务范围内 | P0 |
| FR-2.4 | **追溯矩阵**：自动生成"需求 → 场景 → 任务 → 测试证据"矩阵，面板和报告里展示 | P0 |
| FR-2.5 | **G3 人工批准**：一次性批准设计、风险登记和任务清单；批准后任务清单冻结（记录哈希），之后修改走范围变更申请 | P0 |
| FR-2.6 | **竖切拆分**（引导，不强制）：优先按端到端的薄切片拆任务，先打通最薄的一条链路再加厚，避免"先写完所有数据层再写所有服务层"的横切 | P1 |
| FR-2.7 | **执行计划**：S3 把全部任务分进若干批次，每个批次标明"顺序"或"并行"并写明理由；顺序批次内的任务按列出的顺序执行，并行批次内的任务可以同时开发；后一个批次要等前一个批次全部完成，并行批次还要通过集成检查点 | P0 |
| FR-2.8 | **并行安全检查**：同一并行批次里的任务互不依赖，`scope`、`tests`、`new_files` 两两不重叠，且不碰热点文件（依赖清单和锁文件、路由注册、依赖注入配置、数据库迁移、共享类型与枚举、多语言资源、CHANGELOG 等，可配置）；要改热点文件的工作放进顺序批次 | P0 |

### FR-13 上下文与会话管理

| ID | 需求 | 优先级 |
|---|---|---|
| FR-13.1 | **按执行图派发子 agent**：S4 由主会话按 G3 批准的执行图派发，并行批次的任务和较大的任务派全新的子 agent，顺序批次里的小任务默认由主会话直接做（任务卡的 `run` 字段写明，派子 agent 要写理由）；顺序批次逐个执行，并行批次同时执行（默认最多 3 个），每个并行任务在独立的 git worktree 和分支里开发，批次结束由插件合并并跑集成检查点。派发顺序由插件强制，主会话不能改顺序或跳过批次。子 agent 只拿到任务卡、覆盖的场景、相关上下文片段和验证命令；写入范围就是该任务的范围，规则与主 agent 相同；完成后只回传摘要（改了哪些文件、证据、遗留问题）。遇到需要负责人决定的问题时，子 agent 停下并交回主会话（子 agent 不能用 `ask_user_question`）。守卫无法区分调用方 agent 时，并行批次降级为顺序执行 | P1 |
| FR-13.2 | **测试输出压缩**：识别为测试、构建、lint 的命令，先完整解析出证据，再把进入上下文的输出替换成摘要：运行 / 通过 / 失败 / 跳过数，失败用例名和每个失败的前几行错误，完整日志路径；全文存 `.flowgate/state/evidence/`，agent 需要时可以读取 | P1 |
| FR-13.3 | **交接摘要**：每通过一个门、每完成一个任务，自动生成一段不超过 300 字的交接摘要（已定的决定、当前阶段和任务、未决事项、下一步），写入账本和 `changes/<id>/handoff.md`；开新会话或上下文被压缩后优先注入 | P1 |
| FR-13.4 | **一个变更一个会话**：变更交付归档后提示开新会话；新会话只注入 `project.md`、`roadmap.md`（如有）、相关主规格和最新交接摘要。任意阶段都可以开新会话继续，状态从文件恢复 | P1 |
| FR-13.5 | **上下文占用提示**：宿主能提供 token 用量时，在状态条和面板显示主会话的上下文占用；超过阈值（默认 60%）时提示"建议开新会话"，并预先生成交接摘要 | P2 |

验收场景：

- GIVEN 一次测试输出有 2 万行 WHEN 结果进入上下文 THEN agent 看到的摘要不超过 400 token，且包含失败用例名和完整日志路径。
- GIVEN S4 做到 T3 时开了新会话 WHEN 新会话的第一步 THEN 注入交接摘要和 T3 的任务卡，agent 不用翻旧会话就能接着做 T3。
- GIVEN 派发模式下执行 T3 的子 agent WHEN 它写入 T3 范围外的文件 THEN 被拒绝，规则与主 agent 相同。
- GIVEN 执行图是 B1（顺序：T1 → T2）、B2（并行：T3、T4、T5）WHEN B1 还没完成就请求派发 T3 THEN 被拒绝，并返回当前可以派发的批次。
- GIVEN B2 的三个任务都通过了任务门 WHEN 集成检查点合并后全量测试失败 THEN 不进入下一批，生成一个顺序的修复任务。
- GIVEN 派发模式下子 agent 遇到"优惠券能否叠加"这类未决问题 WHEN 它无法继续 THEN 停下并把问题交回主会话，由主会话用 `ask_user_question` 问负责人。

## 7. 指标体系

| ID | 指标 | 定义 | 目标 | 说明什么 |
|---|---|---|---|---|
| M-1 | 跳步拦截数 | 因"阶段顺序"被拒绝的动作数 | 越早越少越好 | agent 想跳步的频率 |
| M-2 | 实际跳步数 | 未过门禁就进入下一阶段的次数（账本审计） | 0 | 门禁有没有漏 |
| M-3 | 越界尝试数 / 交付时越界残留数 | 范围外写入尝试数；G6 时仍存在的范围外改动 | 残留 = 0 | 过程控制效果 |
| M-4 | 虚假完成拦截数 | 因缺少或过期证据被拒绝的 `flow_task_done` 与被拦下的"宣布完成" | — | 验证纪律 |
| M-5 | 误判率 | 负责人标为误判的拦截 ÷ 全部拦截 | ≤ 5% | 拦截质量 |
| M-6 | 门禁首次通过率 | 各门第一次提交就通过的比例 | 随使用上升 | 产物质量 |
| M-7 | 澄清效率 | 澄清轮数、问题数、自定义回答占比 | — | 提问是否精准 |
| M-8 | 需求返工数 | G1 之后的需求变更次数 | 越少越好 | 需求理解质量 |

## 8. v1.0 完成定义

- 7 个阶段、复杂度 × 风险两个维度的流程等级（低复杂度只需 2 次确认）、人工门、风险接管、单次放行、锁定模式全部可用。
- 从 0 开发可用：项目路线图、工程骨架变更，并在空仓库上演练过"路线图 → C0 → 至少 1 个后续变更"。
- 执行流程图与按图派发可用：顺序批次逐个执行，并行批次在独立 worktree 中同时开发并通过集成检查点。
- 跨会话可用：`.flowgate/` 目录、变更台账、进行状态、自动接续、租约与接管、暂停与恢复。
- 测试输出压缩、交接摘要、一个变更一个会话可用。
- 只在初始化过的项目生效；FlowGate 工程模式可用，受管控会话里原生委派工具已关闭。
- 验证由插件执行并留回执，回执是否过期按输入范围判断；返工按影响范围失效；审查核对读取覆盖。
- 只读分析任务、可核验的源码引用、计划修订、删除与重命名声明、规则沉淀可用。
- 状态条、侧栏 8 个视图、HTML 报告、跨会话看板可用；学习内容覆盖 7 个阶段。
- M-1 ~ M-18 自动计算并可导出。
- 3 个示例仓库（Java、TypeScript、Python）各完成 3 个基准任务，有 / 无插件的对照评测报告已发布。
- 故障注入测试全部通过：宿主启动不受影响；状态损坏后能锁定并恢复；守卫异常时拒绝写入且可见。
