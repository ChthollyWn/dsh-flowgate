## 1. 原始描述（原文照录）

> 我想做一个带有硬约束的dsh插件，功能需要包含 OpenSpec 管规格层（做什么）、Superpowers 管执行纪律层（怎么做）、gstack 管交付闭环层（怎么交付）这三个项目，强制规范vibe coding中的agent开发流程，且需要流程可视化。能将我的模糊描述通过各种角度的精准提问来固化成实际需求，同时按照标准化流程开发和交付。能够包含下面的流程
> - 需求理解：能不能先澄清目标、边界、角色和验收标准，而不是拿到题目就开写。
> - 任务拆解：能不能把大需求拆成 AI 可以独立完成、你也能逐步验收的小任务。
> - 上下文组织：能不能把技术栈、接口约束、目录结构、数据模型和非功能要求说清楚。
> - 过程控制：能不能限制 AI 的修改范围，避免它顺手重构、重复造轮子或改变原有行为。
> - 验证能力：能不能通过 Code Review、测试、日志和运行结果证明功能真的可用。
> - 工程判断：能不能识别安全、性能、成本、合规和可维护性风险，并知道什么时候必须由人接管。

## 4. 由回答推导出的关键取舍

1. **"全部改写"换来了可控，代价是要自己维护方法论。** 不再受上游节奏影响（`superpowers-dsh` 用户反复抱怨"跟上游太慢"），但也拿不到上游的改进。对策：维护一张"方法来源追踪表"，记录每个内置技能借鉴了哪个上游版本的哪个做法，每个季度对照上游发布说明复查一次（不自动同步）。
2. **"个人 + 只在关键节点人工确认"决定了打扰程度。** 一次中复杂度变更里，你只需要做 3 次确认（加上偶发的风险接管和放行），其余全靠证据自动推进。这也意味着自动门的检查必须足够可靠，否则流程会被"自动放过"的错误掏空。
3. **"完整版 + 学习"让可视化和讲解变成了验收条件，而不是锦上添花。** 每个阶段都要有阶段卡（做什么、为什么、合格标准、常见反模式），一次完整变更结束后要能在 HTML 报告里回放全过程。
4. **和昨晚调研结论的冲突及处理。** 竞品调研建议"2 周 MVP 不做 6 维需求拷问"，因为门禁内核的可靠性比功能广度更重要。这次你选了完整版，所以 6 个能力都做，但执行顺序是：先做门禁内核并保证"误伤可解释、失效可见、不炸宿主"（M1），再逐层加深规格层（M2）和执行纪律（M3）。第 6 周的最小版本已经能完整管住"需求 → 计划 → 执行"。

## 7. 追问与补充（2026-10-30 下午）

| Q9 | 非常简单的需求，例如只改前端页面上的一段文案，插件会怎么办？ | ① 小改动（当时的轻量档）仍要 3 次批准，太重；② 没有测试的项目会卡在 G2；③ 你在编辑器里手动改的文件会被算成 agent 越界 | 小改动（现在的低复杂度）把 G1 和 G3 合成一张方案确认卡，加上 G6 一共 2 次确认；`test: none` 的项目改用构建、类型检查和 lint 作基线，并登记"缺少自动化测试"；事后检测改为每次 shell 调用前后各拍一次快照，调用之间的改动记为"非 agent 改动" |

| Q13 | 决定：默认整个 `.flowgate/` 都被 `.gitignore` 排除 | 原默认是除运行态外随代码提交 | 目录内生成内容为 `*` 的 `.gitignore`，不改项目根目录的 `.gitignore`；`git.commit_flowgate` 默认为 false；`git clean -x` / `-X` 列入危险命令 |
