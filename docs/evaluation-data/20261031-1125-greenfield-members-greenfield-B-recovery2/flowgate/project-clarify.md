# 项目级澄清：会员管理系统 v1（可运行 + 登录）

## 目标用户与目标

- 用户：中小门店 / 俱乐部 / 社群的管理员（第一版只有"管理员"一种角色）。
- 场景：管理员在电脑浏览器打开系统，登录后进入后台，查看会员数据（v1 仅登录，会员列表为后续变更）。
- 解决的问题：把会员信息从表格/纸质记录迁到一个可登录、可扩展的 Web 系统；第一版先打通"能启动、能登录"的最小闭环。

## 核心流程

1. 启动服务（`python -m app`）→ 浏览器访问 `http://127.0.0.1:8000/`
2. 未登录被重定向到 `/login`
3. 输入用户名 + 密码 → 校验通过后建立服务端会话
4. 进入受保护首页，显示当前登录用户名与"退出登录"
5. 点退出 → 服务端会话失效 → 再访问首页重新跳转登录页

## MVP 边界（做 / 不做）

**做：**

- 工程骨架：启动入口、配置、SQLite 初始化、健康检查、测试框架、README
- 登录：预置管理员账号、PBKDF2 密码哈希、服务端会话、登录 / 退出、未登录拦截、失败提示、简单限流
- 安全基线：HttpOnly + SameSite=Lax Cookie、随机会话 token、统一错误文案、密码不明文入库
- 自动化测试：登录成功、登录失败、未登录拦截、退出登录

**不做：**

- 开放注册、找回密码、短信 / 邮箱验证码、微信等第三方登录
- 会员增删改查、等级 / 积分 / 标签（C2 起，立项前单独澄清字段）
- 多角色与细粒度权限（C4）、操作审计与导出（C5）
- 支付、营销、消息推送
- 生产级部署（HTTPS 终止、容器、CI/CD）；v1 面向本地 / 内网演示

## 技术栈与部署

- 语言：Python 3.11+，**仅标准库**（`http.server`、`sqlite3`、`hashlib`、`hmac`、`unittest`），零第三方依赖
- 存储：SQLite 单文件 `data/app.db`（不入版本库）
- 页面：服务端渲染 HTML，无前端构建链
- 启动：`python -m app`，默认 `127.0.0.1:8000`，端口可用 `PORT` 覆盖
- 部署：v1 只要求本机 / 内网可运行；README 写明后续可替换为 WSGI 框架

## 非功能要求

- 安全：密码 PBKDF2-HMAC-SHA256 + 随机 salt；会话 token 随机且服务端存储；Cookie HttpOnly、SameSite=Lax、Path=/；登录失败统一提示"用户名或密码错误"；同一用户名 5 分钟 5 次失败限流；登录成功后轮换会话
- 性能：本地单实例，1000 名会员规模下页面响应 < 500ms
- 可用性：单进程即可启动，无外部依赖；启动失败有清晰错误信息
- 合规：只存登录与会员必要信息，不采集敏感个人信息；日志不打印密码或会话 token

## 约束与未知项

- 约束：仓库当前只有 README，无任何代码 / 构建 / 测试；无既定技术栈；不假设可联网安装依赖
- 未知项（不阻塞，先按默认执行，负责人可随时改）：
  - Q1 技术栈：默认 Python 标准库方案（零依赖优先）
  - Q2 登录标识：默认用户名（非手机号 / 邮箱）
  - Q3 是否开放注册：默认不开放，仅启动时创建预置管理员
  - Q4 会员字段：v1 不建业务表，C2 立项前再澄清
  - Q5 是否需要多角色：v1 只有管理员，C4 再拆
- 风险：鉴权是高风险面（弱口令、会话固定、暴力破解）；`http.server` 不适合公网生产。对策写入 C1 验收项，README 明确适用边界。

## 验收标准（v1 完成定义）

1. `python -m app` 可启动，监听 `127.0.0.1:8000`
2. `GET /healthz` → `200 {"status":"ok"}`
3. 未登录 `GET /` → `302` 到 `/login`
4. 正确凭据 `POST /login` → `302` 到 `/`，首页显示用户名
5. 错误凭据 → `200` 且含错误提示，不建立会话
6. `POST /logout` 后 `GET /` 再次 `302` 到 `/login`
7. `python -m unittest discover -s tests` 全绿，覆盖第 3–6 条
8. `data/`、`__pycache__/` 已加入 `.gitignore`；README 写清启动方式与账号来源
