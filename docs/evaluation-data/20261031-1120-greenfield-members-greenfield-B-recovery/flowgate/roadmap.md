## C0 工程骨架（第一个变更）

只做“能启动、能测试”的地基，不实现业务登录：

- `package.json`：`start`、`test`、`check` 脚本，声明 Node 版本。
- `src/server.js`：HTTP 服务入口，支持 `PORT`、`HOST` 环境变量。
- `src/app.js`：请求路由与静态资源处理骨架，提供 `GET /healthz`。
- `test/health.test.js`：健康检查自动化测试。
- `README.md`：本地启动、测试、环境变量说明。
- `.gitignore`、`.env.example`：排除运行时数据与密钥。

验收：在干净环境执行 `npm start` 后访问 `/healthz` 得到 `200 {"status":"ok"}`；`npm test` 通过。

## C1 登录、会话与会员总览（V1 核心）

- 预置管理员：首次启动初始化账号，密码 scrypt 哈希存储。
- 登录页与 POST 登录：统一错误文案、失败限流。
- 会话：随机 Session ID + `HttpOnly`/`SameSite=Lax` Cookie，服务端内存存储。
- 受保护页面：未登录 302 到 `/login`；已登录渲染会员总览。
- 退出登录：销毁服务端会话并清除 Cookie。
- 只读会员名册：虚构示例数据，手机号脱敏展示。
- 集成测试：登录成功、错误密码、未登录拦截、退出失效。

验收：按 README 启动后可用 `admin` / `admin12345` 登录，看到会员总览；退出后无法直接访问总览。

## 交付节奏

1. C0 通过后立即进入 C1，形成可登录的 V1 闭环。
2. C1 验收后由负责人实际试用，再决定是否进入 C2。
3. 每个变更独立立项、独立验收；不把后续会员维护能力提前塞进 V1。

## 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 零依赖自建 HTTP 层缺少框架能力 | 路由/解析需自己保证正确性 | 保持路由极简；用集成测试覆盖关键路径 |
| JSON 文件并发写入 | 多请求同时写可能丢数据 | 首版只读会员数据，写入仅初始化；C2 改为串行写/数据库 |
| 内存会话重启丢失 | 重启后需重新登录 | 首版明确接受，C4 再持久化 |
| 默认演示密码被误用于生产 | 账号被轻易接管 | README 显著警告；生产环境必须用环境变量覆盖 |
