提案

为什么做什么影响不做
待办列表翻到最后一页时会看到前面已经出现过的条目。根因是 `paginate` 把起始下标夹到 `items.length - pageSize`，当总数不能被 `pageSize` 整除时，最后一页会回退到上一页的区间并与上一页重叠（`src/pagination.js:26-31`、`README.md:19-22`）。此外 `sortTodos` 在 `createdAt` 相同时缺少稳定的第二排序键，可能让同一批数据在不同页之间顺序漂移（`src/pagination.js:33-36`）。1. `paginate` 改为按 `(page - 1) * pageSize` 直接计算起始下标，只返回剩余条目；页码超出总页数时自然返回空数组，不回退到最后一页。 2. `sortTodos` 在 `createdAt` 倒序基础上，对 `createdAt` 相同的条目按 `id` 升序稳定排序。 3. 保持 `buildPage` 的响应字段与 `hasNext` 语义不变，并补充/运行回归测试覆盖最后一页、越界页与相同 `createdAt` 排序。- 仅影响 `src/pagination.js` 的分页与排序逻辑，以及对应测试。 - `GET /todos` 的响应字段、HTTP 状态码与路由不变（`src/server.js:68-74`）。 - 不涉及鉴权、报表、提醒模块，不引入新依赖。不改变 `page` / `pageSize` 参数名、默认值或 `MAX_PAGE_SIZE` 上限。；不调整 `/todos` 的过滤条件（`ownerId` / `completed`）与排序方向（仍为最新在前）。；不重构 `TodoStore`、不改持久化结构、不修改其他模块。

数据流 / 错误处理

数据流：`GET /todos` → `server.js` 读取 `page` / `pageSize` 与过滤参数（`src/server.js:68-73`）→ `TodoStore.list` 过滤得到数组（`src/store.js:30-37`）→ `buildPage`： 1. `sortTodos(todos)` 复制数组，按 `createdAt` 字符串倒序，相同则按 `id` 字符串升序； 2. `normalizePaging` 归一化页码与页大小（`1..10`）； 3. `paginate` 以 `start = (page - 1) * pageSize`、`end = start + pageSize` 切片； 4. 组装 `{ items, page, pageSize, total, hasNext }` 返回。 示例：10 条、`pageSize=3` → 第 1 页 3 条、第 2 页 3 条、第 3 页 3 条、第 4 页 1 条（`todo-001`）、第 5 页空数组。

错误处理：- 不新增异常路径：`page` / `pageSize` 为 `undefined`、非数字、`< 1` 时仍由 `normalizePaging` 回落到 `1` / `3`（`src/pagination.js:11-17`）。 - `page` 超过总页数时 `slice` 自然返回 `[]`，`total` 仍为真实总数，`hasNext` 为 `false`，不抛错。 - 空列表返回 `items: []`、`total: 0`、`hasNext: false`。 - 不改变 `createApp` 的统一异常捕获与 `500` 行为（`src/server.js:128-133`）。
