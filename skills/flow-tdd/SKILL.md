# flow-tdd：测试驱动（S4 任务内）

## 何时用

- 任务卡 `tdd: required`：改实现文件之前必须先有失败测试的 RED 回执。
- 高风险变更：全部任务 TDD 必需，豁免要负责人批准。
- 低复杂度逻辑修改：建议先写测试；纯文案/样式任务可豁免（在任务卡写理由）。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 测试文件 | 任务卡 `tests` 声明的范围 | 只能写声明过的测试范围 |
| RED / GREEN 回执 | 插件证据库 `.flowgate/state/evidence/<id>.log` + 摘要 | 只有 `flow_verify` 产生的回执算证据 |
| TDD 状态 | `.flowgate/changes/<id>/status.json` 的 `tdd` 字段 | 插件维护 `none / red / green` |

## 步骤（照做即可）

1. **读任务卡与场景。** 明确这个任务要覆盖哪些场景（`covers`）、验证组命令是什么、`inputs` 覆盖哪些文件。TDD 的断言要能直接对应场景的 THEN。
2. **先写测试。** 在任务卡声明的 `tests` 范围里写最小失败测试：
   - 一个测试只验证一个行为，名字写清"场景 + 期望"；
   - 优先测行为（接口返回、状态变化、存储结果），少测内部实现；
   - 只写能失败的最小集合，不提前写未来需求的测试；
   - 不改动实现文件（写了实现文件会被拦）。
3. **跑出 RED。** 调用 `flow_verify({ taskId, group })` 运行该任务的验证组。合格 RED 的标准：命令可解析、运行数 ≥ 1、失败数 ≥ 1。回执会自动记录；这是后续编辑实现文件的前置条件。
4. **写最小实现。** 只改任务卡 `scope` 内的源码，让测试变绿；不顺手重构，不提前实现未覆盖的需求。
5. **跑出 GREEN。** 再次 `flow_verify`，要求通过数 ≥ 1、失败数 = 0，且输入（源码、测试、构建配置）自 RED 以来没有变化被遗漏——回执按 `inputs` 的哈希判断是否过期。
6. **在绿灯下重构。** 需要整理结构时保持 GREEN：重构后重新 `flow_verify`，拿到新回执；旧回执在输入变化后自动过期。
7. **记录说明。** 需要补充非自动可验证的背景时用 `flow_attach_evidence({ kind, path, note })`，它会标为"agent 自述"，不能代替 `flow_verify` 回执。
8. **交给下一个技能。** GREEN 后运行 `flow-review`（按风险与复杂度决定是否逐任务审查），再 `flow_task_done`。

## 合格标准（可对照检查）

- [ ] 写实现前已有 RED 回执：运行数 ≥ 1、失败数 ≥ 1。
- [ ] RED 的失败原因与任务场景一致（不是环境错误、不是语法错误）。
- [ ] 实现只做让测试变绿的最小改动，范围在任务卡内。
- [ ] GREEN 回执新鲜：通过数 ≥ 1、失败数 = 0，产生在最后一次改动之后。
- [ ] 测试断言可对应场景的 THEN，不是"不抛异常就算过"。
- [ ] 没有修改或删除既有测试来让结果变绿；没有跳过/禁用测试。
- [ ] 重构后重新跑过验证，回执不过期。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| TDD 任务在 RED 之前编辑实现文件 | 写入被拒绝，提示"先写失败的测试并运行它" |
| RED 回执必须有失败用例且运行数 ≥ 1 | 不认可为 RED；运行 0 个测试的结果不算证据 |
| GREEN 回执必须新鲜（按验证组 inputs 哈希） | `flow_task_done` 被拒绝，提示回执已过期、需要重新 `flow_verify` |
| 同一验证组以最新一次为准 | 更早的通过不能覆盖之后的失败 |
| TDD 必需范围按风险等级确定（高风险全部必需） | 未满足时任务门不通过；豁免需负责人批准 |
| 删除/跳过测试、删减断言、改测试配置 | 标记为篡改检测项，交审查并在 G6 列出 |
| 验证由插件执行 | agent 自己跑的测试只作参考，不算 RED/GREEN 证据 |

## 只做引导的部分

- 怎样写"最小失败测试"：选什么断言、怎么命名、测到哪一层。
- 什么时候该拆成多个测试、什么时候合并。
- 重构的时机与边界。
- 哪些任务不适合 TDD（纯配置、纯文案）以及如何在任务卡里说明理由。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 先写实现，再补测试 | 测试会不自觉地贴合实现，失去验证意义 | 先写测试并跑出 RED |
| 测试一写就绿 | 说明它没验证新行为，或实现已经存在 | 检查断言是否真的对应新需求 |
| 一个测试断言十件事 | 失败时不知道哪条需求坏了 | 拆成多个行为单一的小测试 |
| 为了变绿改测试/删断言/加 skip | 证据造假，审查与 G6 会暴露 | 修实现，不改判定标准 |
| 用 agent 自己跑的命令当证据 | 不算 RED/GREEN；插件不认 | 用 `flow_verify` |
| 重构后不重新验证 | 回执过期，任务门不通过 | 重构后重新 `flow_verify` |
| 把整个类的所有测试一次写完 | 失去 TDD 的反馈节奏 | 每个行为一轮 RED → GREEN |

## 正例

任务 T3 覆盖 R2.S1（重复回调不生效）。先写测试 `RenewalCallbackTest.repeatCallbackKeepsExpireDate`，只断言"再次回调后到期日不变且返回 200"，`flow_verify` 得到 RED（1 失败）；然后在 `RenewalIdempotencyGuard` 里加唯一索引查询并返回已处理，`flow_verify` 得到 GREEN；再把重复逻辑抽成方法，重构后重新验证仍 GREEN。

## 反例

agent 先实现幂等逻辑，再写一个断言"回调不抛异常"的测试；测试一写就绿；然后为了"证明 TDD"把测试注释掉再跑一次 RED。结果：RED 回执与任务场景无对应关系，删测试触发篡改检测，任务门不通过，审查也会指出"测试未覆盖 R2.S1"。

## 与其他技能的衔接

- 测试设计来自 `flow-plan` 的任务卡；上下文来自 `flow-context`。
- 失败排障用 `flow-debug`；越界测试文件用 `flow-scope`。
- 完成后用 `flow-verify` 做收尾验证，用 `flow-review` 接受审查。
