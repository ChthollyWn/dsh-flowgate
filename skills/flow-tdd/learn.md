# 学习卡：S4 执行（TDD 纪律）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

对任务卡要求的 TDD 任务：先在任务卡声明的测试范围里写一个最小失败测试，用 `flow_verify` 跑出 RED 回执（运行数 ≥ 1、失败数 ≥ 1），再写最小实现拿到 GREEN 回执（失败数 = 0、通过数 ≥ 1），最后在绿灯下重构并重新验证。RED/GREEN 回执由插件产生，是唯一被认可的过程证据。

## 为什么（why）

先写实现会诱使测试迁就实现，测试从"验证需求"退化成"描述现状"，回归保护失效。先失败再通过，能证明测试真的覆盖了新行为；同时 RED 是一个明确的"我理解了需求"的信号。代码强制 RED 才能改实现，是因为靠自觉无法稳定做到——这是把工程纪律变成流程约束的典型场景。

## 合格标准（criteria）

- 改实现前有 RED 回执，失败原因与场景一致。
- 实现是最小改动，范围在任务卡内。
- GREEN 回执新鲜（输入哈希未变），通过数 ≥ 1、失败数 = 0。
- 断言对应场景 THEN，不弱化、不删除、不跳过测试。
- 重构后重新验证，旧回执不当作新证据。
- 最终任务门通过，审查无"缺少测试"发现。

## 对应上游做法（upstream）

- Superpowers 的 test-driven-development：红 → 绿 → 重构的循环，一次只走一小步。

FlowGate 的改写：把"RED 才能改实现、GREEN 必须新鲜、测试篡改检测、验证由插件执行"写进守卫与任务门；把"怎么写出好的最小测试"留作引导。这样 TDD 不再只是提示词里的建议。

## 常见反模式（antiPatterns）

- 先写实现再补测试，测试贴合现状。
- 测试一写就绿，没有验证新行为。
- 一个测试断言太多，失败定位困难。
- 为了绿改测试、删断言、加 skip。
- 拿 agent 自己跑的命令当 RED/GREEN 证据。
- 重构后不重新验证。
- 一次写完全部测试，失去 TDD 反馈节奏。

## 正例（good）

`RenewalCallbackTest.repeatCallbackKeepsExpireDate` 先写、先跑，RED（1 失败例）；实现里加幂等查询与唯一索引兜底，GREEN（1 通过）；再抽出重复处理逻辑，重构后重跑仍 GREEN。整个过程 RED/GREEN 回执齐全，审查一次通过。

## 反例（bad）

先写完整实现，再补一个"回调不抛异常"的测试，测试一写就绿；为了凑 RED 把测试注释掉跑一次。结果：回执与场景不匹配、删除测试触发篡改检测、任务门被拒、审查指出测试未覆盖幂等场景。
