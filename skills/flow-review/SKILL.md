# flow-review：代码审查（S4–S5）

## 何时用

- S4 每个任务拿到 GREEN 之后（按复杂度与风险决定是否逐任务审查）：
  - 普通风险：低复杂度不逐任务审查，S5 做一次终审；中、高、超高复杂度每个任务一轮综合审查；
  - 高风险：每个任务两轮——先"是否符合规格"，再"代码质量"；S5 终审加安全审查。
- S5：全量验证通过后做终审。
- 审查发现的重复问题 → 规则沉淀（需要负责人批准）。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 审查结论 | `.flowgate/changes/<id>/review.md` | **插件写**，agent 不手写 |
| 规则提议 | `.flowgate/rules/<rule-id>.md` | 负责人批准后由插件写入 |
| 待处理项 | 账本 + 面板 | major 豁免、规则提议需要人工决定 |

## 步骤（照做即可）

1. **先让被审对象干净。** 任务范围小、diff 可读、没有调试残留、验证是新鲜的 GREEN。审查输入是任务卡、覆盖的场景、`context.md` 相关片段和该任务的 diff，不是整个会话。
2. **等插件启动审查。** 审查子 agent 是干净上下文、只读（read / grep / glob / `flow_diff`）的独立 agent；插件核对它的读取记录是否覆盖全部待审文件和 diff——被截断、漏读的审查不算数，会要求重审。你不需要也不应该自己去"催审"。
3. **读审查结论。** 结论是结构化的：`verdict`（pass / changes-required）+ `findings[]`（severity、file、line、rule、message、suggestion）。规则类别包括 spec-mismatch、missing-test、duplicate-logic、unrelated-change、error-handling、security、naming。
4. **按严重级别处理：**
   - **critical**：任务门不通过，必须修复；修完重新验证、重新审查。
   - **major**：修复，或由负责人在面板豁免并写理由；不能自行忽略。
   - **minor**：记录，出现在报告里；能顺手修就修，但要保持范围。
5. **逐条回应。** 对每条 finding 说明：改了什么、在哪个文件/行、用什么证据验证。不要只说"已修复"或"这个是风格问题"——审查看的是事实。
6. **修完重跑验证。** 修复后 `flow_verify` 拿新 GREEN；改动较大时审查结论也会失效，需要重新审查。
7. **不要试图让审查变松。** 不要要求审查子 agent 放宽标准、不要关闭它的检查、不要自己写 `review.md`。审查结论由插件根据结构化输出写入。
8. **S5 终审。** 全量验证通过后确认：无未处理 critical / major；高风险加一轮安全审查（OWASP 常见问题、密钥、注入、鉴权绕过）；终审通过才能进 S6。
9. **规则沉淀。** 审查发现里"真实、已修复、以后还会出现"的问题，用 `flow_propose_rule({ finding, rule, example, scope })` 提交 `RL-n`，负责人批准后成为项目规则；一次性的误判不沉淀。
10. **豁免要留痕。** major 由负责人豁免时，理由会进报告；agent 不要把豁免当成"可以不改"的默认选项。

## 合格标准（可对照检查）

- [ ] 审查前任务是新鲜 GREEN、diff 干净、没有调试残留。
- [ ] 审查覆盖完整：审查子 agent 实际读完了全部待审文件和 diff。
- [ ] 所有 critical 已修复并重新验证。
- [ ] 所有 major 已修复，或有负责人书面豁免。
- [ ] minor 已记录，修复的没有越界。
- [ ] 修复后重新验证，证据新鲜。
- [ ] S5 终审无未处理 critical / major；高风险安全审查已完成。
- [ ] 重复问题已提议为规则（在负责人批准前不生效）。
- [ ] 没有自己写 `review.md`、没有要求审查放水。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 审查子 agent 只读（read / grep / glob / `flow_diff`） | 只能读取待审内容，无法改代码 |
| 读取覆盖核对（截断、漏读不算） | 审查无效，要求重审 |
| 只认结构化输出 | 自由文本或 schema 校验失败不算有效审查 |
| critical 阻断任务门 | 不修复不能完成任务 |
| major 需修复或人工豁免 | 未处理则任务门不通过 |
| 审查轮次按风险（高风险两轮 + 终审安全审查） | 按配置执行，不能跳过 |
| 审查启动失败不消耗轮次 | 可重试 |
| 同一 diff 指纹不重复审查 | 由插件控制成本 |
| 规则沉淀需负责人批准 | 未经批准规则不生效；进行中变更按冻结契约不受影响 |

## 只做引导的部分

- 怎样回应审查意见、怎样判断一条意见是否合理。
- 怎样写修复说明让人信服。
- 哪些问题值得沉淀成规则、规则怎么写才有用。
- 怎样看待"风格类"意见（可修可记，但要说明理由）。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 不修 critical 就宣称完成 | 任务门必拦截，交付也会失败 | 先修 critical 并重新验证 |
| 把 major 当 minor 忽略 | 豁免需要负责人书面同意 | 修复或申请豁免 |
| 修复后不重新验证 | 证据过期，任务门不通过 | 重新 `flow_verify` |
| 让审查子 agent "通融一下" | 审查只读，无法被说服；且失去意义 | 用事实回应 |
| 自己写 `review.md` | 受保护文件，写入被拒绝 | 由插件写 |
| 只回应"已修复"不给证据 | 无法验证，等于没修 | 给文件/行 + 验证结果 |
| 把一次性误判沉淀成规则 | 规则库噪音变大 | 出现两次以上的问题再提议 |

## 正例

审查发现 critical"R2.S1 的重复回调没有测试覆盖"、major"幂等查询没有索引，数据量大时会全表扫描"、minor"变量名 txn 不易读"。agent 修 critical：补 `repeatCallbackKeepsExpireDate` 测试并验证 RED→GREEN；修 major：加唯一索引迁移并跑迁移测试；minor 记录在报告里顺带改名。逐条回应后重跑验证，审查二次通过；随后把"回调类需求必须覆盖重复调用场景"提议为规则。

## 反例

审查给出 1 个 critical（改动与 R2 场景不符）和 2 个 major。agent 回复"已确认，都是风格问题"，没有修代码；任务门被 critical 阻断后，它自己新建了一个 `review.md` 写"复检通过"，写入被拒绝；最后它把测试断言改弱后重新提交，被篡改检测标记。结果交付被卡在 S5。

## 与其他技能的衔接

- 审查前用 `flow-verify` 拿证据；审查后修复再验证。
- 规则沉淀在 `flow-review` 提议、`flow-retro` 复盘确认有效性。
- S5 终审通过后进入 `flow-ship`。
