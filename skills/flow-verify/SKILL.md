# flow-verify：验证与证据（S4–S5）

## 何时用

- S4 每个任务在 `flow_task_done` 之前：确认验证组有新鲜 GREEN。
- S4 TDD：需要 RED 与 GREEN 回执时。
- S5：全量测试与基线对比、验收场景证据、运行证据。
- 任何时候准备说"完成了"之前——先看有没有新鲜证据。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 验证回执 | 插件记账 + `.flowgate/state/evidence/<id>.log` | 命令、退出码、运行/通过/失败/跳过数、输入哈希、完整输出路径 |
| 证据摘要 | `.flowgate/changes/<id>/evidence.md` | 插件写 |
| 手工证据 | `flow_attach_evidence` 的 `path` + 记录 | 标"agent 自述"，高风险时需 G6 逐条确认 |

## 步骤（照做即可）

1. **选对验证组。** 用任务卡 `verify` 里声明的组：`group`、`command`、`inputs` 都来自任务卡；不要临时换命令或只跑一个测试文件来"证明"。
2. **调用 `flow_verify`。** `flow_verify({ taskId, group })` 由插件执行命令并解析输出：优先读机器可读报告（JUnit XML、pytest junitxml、Vitest/Jest JSON、`go test -json`），否则解析控制台。回执记录命令、退出码、运行数、通过数、失败数、跳过数、输入哈希、起止时间、完整日志路径。
3. **判断证据有效性：**
   - 运行数为 0 不算证据（FR-5.2）；
   - 回执按 `inputs` 的文件哈希判断新鲜度；输入变了回执自动过期；
   - 同一组以最新一次为准，更早的通过不能覆盖之后的失败；
   - 只有 `flow_verify` 产生的回执算 RED/GREEN 证据，agent 自己跑的测试只作参考。
4. **读懂失败。** 摘要给你失败用例名 + 每例首行错误 + 完整日志路径；先读日志再改代码，按 `flow-debug` 排障。修完后重新 `flow_verify`，不要用旧回执交差。
5. **TDD 证据链。** 需要 TDD 的任务：RED（失败数 ≥ 1）在实现改动之前，GREEN（失败数 = 0、通过数 ≥ 1）在最后一次改动之后。
6. **S5 全量验证。**
   - 跑全量测试并与 S2 基线对比：基线通过、现在失败的测试必须为 0，除非它们被 MODIFIED / REMOVED 需求覆盖且经负责人确认；
   - lint / build 按 `project.md` 声明的命令执行；
   - 逐条核对验收场景：每个场景要有通过证据；没有自动化覆盖的场景用 `flow_attach_evidence` 附手工证据（截图、日志），标黄并由负责人在 G6 确认。
7. **运行证据（按风险）。** 有运行命令时（`commands.run` / `health`）：
   - 用声明的命令启动服务并等待就绪，做健康检查；
   - 按验收场景走关键路径（HTTP 请求、CLI 命令，浏览器工具存在时可截图）；
   - 记录状态码、响应片段、日志路径，停止服务；
   - 普通风险：有运行命令时必需；高风险：必需（日志 + 冒烟）。
8. **不要宣称完成。** 如果没有新鲜 GREEN 却说"全部通过、已完成"，轮次结束时插件会让轮次继续并要求验证（每轮最多 2 次）。按提示 `flow_verify`，用输出证明。
9. **返工范围。** 缺陷返工只让受影响任务的回执失效（沿依赖向下扩散）；需求或方案变更、影响不明时全部失效。重跑受影响的验证组，不要无差别全跑。

## 合格标准（可对照检查）

- [ ] 每个任务完成前有新鲜的 GREEN 回执（通过数 ≥ 1、失败数 = 0）。
- [ ] RED/GREEN 的先后顺序符合 TDD 要求。
- [ ] 回执没有过期：`inputs` 在回执产生后没有变更。
- [ ] S5 全量结果与基线对比无新增回归。
- [ ] 每个验收场景都有证据：自动化回执或经确认的手工证据。
- [ ] 运行证据符合风险要求，且用了声明过的命令。
- [ ] 没有用 agent 自跑结果、旧回执、0 测试结果冒充证据。
- [ ] 失败用例不是通过改测试/跳过测试"解决"的。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 验证命令只能来自任务卡验证组或 `project.md`，且形状合法 | 不合法命令不能执行；`&&`、`\|\|`、`;`、管道、重定向、命令替换会被拒绝 |
| 运行数为 0 不算证据 | 回执标记无效，不能用于任务门 |
| 回执按 `inputs` 哈希判断是否过期 | `flow_task_done` 被拒，提示回执过期、需要重新 `flow_verify` |
| 同一组最新一次为准 | 旧通过不能覆盖新失败 |
| TDD 任务需要较早 RED + 新鲜 GREEN | 任务门不通过 |
| 轮次结束前声称完成但缺新鲜证据 | 轮次继续并要求验证（每轮最多 2 次） |
| S5 与基线对比、回归必须为 0（除非被需求覆盖并确认） | G5 失败，列出回归测试 |
| 运行证据按风险必需 | G5 失败或标缺失 |
| 手工证据标"agent 自述"、高风险 G6 逐条确认 | 不能当作自动化证据；G6 要求确认 |
| 完整日志本地保存、摘要 ≤ 400 token | 由插件执行压缩 |

## 只做引导的部分

- 什么命令能证明什么（单元测试证明逻辑、集成测试证明协作、运行证据证明可用）。
- 冒烟检查怎么设计、选哪些场景。
- 手工证据怎么采集才可信。
- 如何读失败日志、何时该补测试而不是重跑。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| "应该能跑" / "我本地跑过了" | 没有证据，不算完成 | `flow_verify` 拿回执 |
| 拿几小时前的测试结果说事 | 回执已过期，不能证明当前代码 | 重新验证 |
| 只测成功路径 | 失败路径最容易出问题 | 覆盖场景的错误分支 |
| 只跑一个相关测试文件 | 全量回归未验证 | 任务门用声明组，S5 跑全量 |
| 运行 0 个测试也算通过 | 没验证任何行为 | 确认测试被真实执行 |
| 改测试/跳过测试让失败消失 | 证据造假，审查与 G6 暴露 | 修实现 |
| 没有运行命令却声称"已验证运行" | 验收场景无证据 | 用 `flow_attach_evidence` 手工证据并标清 |
| 返工后无差别全量重跑 | 浪费时间；应按影响范围失效 | 只重跑受影响验证组 |

## 正例

T3 完成前：`flow_verify({ taskId: "T3", group: "renewal-unit" })` → 通过 12、失败 0、运行 12、输入哈希 H，日志路径已记录；随后又改了 `RenewalPolicy`（在 `inputs` 内），回执过期 → 重新 `flow_verify`。S5：全量组跑出 84 通过 0 失败，与基线对比无新增失败；启动服务做健康检查并用两条验收场景请求冒烟，日志路径附入证据；G5 一次通过。

## 反例

agent 在回复里写"全部测试通过，已完成"，但它跑的是自己终端里的 `pnpm test`，插件没有回执；`flow_task_done` 被拒。它又贴了 10 分钟前的回执——输入已变，回执过期。轮次被延长要求验证，前后浪费两轮。

## 与其他技能的衔接

- TDD 的 RED/GREEN 由本技能产生（`flow-tdd`）。
- 失败排障走 `flow-debug`；运行烟测由 `flow-qa` 负责。
- S5 之后进入 `flow-ship`；审查结论由 `flow-review` 给出。
