# 学习卡：S4–S5 验证能力

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

验证由插件执行：`flow_verify` 运行任务卡声明的验证组，记录命令、退出码、运行/通过/失败/跳过数、输入哈希和完整日志路径，产生唯一的 RED/GREEN 证据。任务完成前要求新鲜 GREEN；S5 跑全量测试并与 S2 基线对比、逐条覆盖验收场景，并按风险提供运行证据（启动服务、健康检查、冒烟）。

## 为什么（why）

"应该能跑"是 agent 最常见的虚假完成。让插件亲自执行命令，证据里就有退出码和测试计数，旧结果还会因输入变化自动过期；S5 与基线对比，则能发现"新功能对了，但把旧行为改坏了"。运行证据补上自动化测试覆盖不到的"服务真的能用"，避免交付后才发现起不来。

## 合格标准（criteria）

- 任务完成前有新鲜 GREEN 回执；RED/GREEN 顺序符合 TDD。
- 回执未过期（inputs 未变），同组最新一次为准。
- S5 相对基线无新增回归；lint/build 通过。
- 每个验收场景都有自动化或经确认的手工证据。
- 运行证据符合风险要求，使用声明命令。
- 没有用自跑结果、旧回执、0 测试结果冒充证据。

## 对应上游做法（upstream）

- Superpowers 的 verification-before-completion：在宣布完成之前必须运行验证，并用输出作为证据。

FlowGate 的改写：把"验证由插件执行、证据按输入判断过期、0 测试不算证据、轮次结束拦截虚假完成、S5 与基线对比、运行证据按风险必需"变成代码强制。这样"完成"有了客观定义，模型无法用语言绕过。

## 常见反模式（antiPatterns）

- "应该能跑""我本地跑过了"，没有回执。
- 拿过期回执或旧测试结果说事。
- 只测成功路径、只跑一个测试文件。
- 0 个测试的运行也算通过。
- 改测试或跳过测试让失败消失。
- 没有运行命令却声称运行验证过。
- 返工后无差别全量重跑。

## 正例（good）

T3 用 `flow_verify` 得到 12 通过 0 失败；改了一处输入内文件后回执过期，重新验证得到新 GREEN。S5 全量 84 通过 0 失败、与基线对比无回归；启动服务做健康检查，按两条验收场景发请求并记录状态码与日志；G5 一次通过。

## 反例（bad）

agent 宣称"全部测试通过、已完成"，但没有任何回执；被拒后贴了 10 分钟前的旧结果，输入已变被判定过期；它又跑了一个只含 1 个测试的文件想蒙混，运行数虽为 1 但与验证组不一致，任务门仍不通过。两轮时间被浪费，验证纪律没有建立起来。
