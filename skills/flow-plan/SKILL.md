# flow-plan：任务拆解与执行计划（S3）

## 何时用

- 每次变更进入 S3：写 `tasks.md`（任务卡 + 执行计划），交 G3 批准。
- 执行中发现要追加任务或调整未开始任务的顺序：用 `flow_request_plan_change`（计划修订），不要直接改已冻结的 `tasks.md`。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 任务卡 + 执行计划 | `.flowgate/changes/<change-id>/tasks.md` | agent（G3 后冻结） |
| 执行流程图 | `.flowgate/changes/<change-id>/execution-plan.md` | **插件生成**，agent 不手写 |
| 追溯矩阵 | 插件自动生成，面板与报告展示 | 插件 |

## 步骤（照做即可）

1. **按竖切拆任务。** 优先拆成端到端的薄切片（一条链路从入口到存储到返回打通），再逐层加厚；避免"先写完所有数据层，再写所有服务层"的横切。每个任务应能独立完成、独立验收。
2. **写任务卡。** 每张卡使用 03 文档 §9.3 的字段：

   ```yaml
   covers: [R2.S1, R2.S2]        # 必须覆盖至少一个场景；chore 任务写理由
   scope: [src/renewal/**]        # 源码范围，不能是仓库根
   tests: [test/renewal/**]       # 测试范围
   new_files: [src/renewal/IdempotencyGuard.java]  # 必须在 scope 内
   changes: [{ path: ..., kind: delete }]          # 删除/重命名必须先声明
   depends_on: [T1]
   tdd: required                  # required | recommended | exempt（exempt 要理由）
   verify:                        # 验证组，由插件执行
     - group: renewal-unit
       command: ./mvnw -B -q -Dtest=RenewalCallbackTest test
       inputs: [src/renewal/**, test/renewal/**, pom.xml]
   run: subagent                  # main | subagent；subagent 要写 run_reason
   size: M                        # S ≤ 2 文件 / M ≤ 5 文件；超了拆
   risk: [payment]
   ```

3. **控制规模。** 单任务 ≤ 5 个文件、预计 ≤ 200 行改动；一个变更 ≤ 12 张任务卡，超过拆成多个变更。范围不要写成 `src/**`；`new_files` 用模块级通配也必须落在 `scope` 内，不能是根级通配。
4. **写验证命令。** 每个任务至少一个验证组；命令来自任务卡或 `project.md`，不能带 `&&`、`||`、`;`、管道、重定向、命令替换；`inputs` 覆盖源码、测试、构建配置和依赖锁文件（决定回执是否过期）。
5. **保证追溯全覆盖。** 每个场景至少被一张任务卡覆盖；每张任务卡至少覆盖一个场景（纯 chore 写清理由）。自查一遍追溯矩阵，不要留空格。
6. **排执行计划。** 在 `tasks.md` 末尾写 `execution:`：
   - 每个任务恰好出现在一个批次里；
   - `depends_on` 只能指向更早批次或同顺序批次里更靠前的任务；同一并行批次内互不依赖；
   - 并行批次里任意两个任务的 `scope` / `tests` / `new_files` 不重叠；
   - 并行批次不能碰热点文件（依赖清单与锁文件、路由注册、依赖注入配置、数据库迁移、共享类型与枚举、多语言资源、CHANGELOG；默认清单见 `config.yaml`，可追加）；
   - 每个批次写 `why`：为什么必须顺序，或为什么可以并行。
7. **决定谁执行。** `run: main` 用于小任务；`run: subagent` 要写理由（需要并行、需要隔离上下文或需要独立核对），文件彼此独立本身不是理由。`dispatch: auto` 时并行任务和规模 M 的任务默认派子 agent。
8. **自检后提交 G3。** `flow_submit({ gate: "G3" })`。G3 会检查任务卡、追溯、规模、执行计划并行安全和热点文件；失败按 `failures[].hint` 修。负责人批准后任务清单冻结（记录哈希），执行图自动生成。
9. **执行中要改计划。** 追加任务或调整未开始任务的顺序用 `flow_request_plan_change({ add, reorder, reason })`，生成 `PC-n` 由负责人批准；已开始和已完成的任务不能改。
10. **发现范围不够。** 不要偷偷扩大任务范围；用 `flow_request_scope_change`（`flow-scope`）。

## 合格标准（可对照检查）

- [ ] 每张任务卡字段完整：id、标题、covers、scope、tests、new_files、depends_on、tdd、verify、run、size、risk。
- [ ] 覆盖场景无遗漏，chore 任务有理由。
- [ ] 所有任务范围精确（不是仓库根），新文件落在范围内。
- [ ] 每张卡 ≤ 5 个文件；变更 ≤ 12 张卡。
- [ ] 每个任务至少一个验证组，命令形状合法，`inputs` 覆盖源码/测试/构建配置。
- [ ] 执行计划每个任务只出现一次，依赖顺序合法，并行批次范围不重叠、不碰热点文件，每个批次有 `why`。
- [ ] 没有手写执行流程图（由插件生成）。
- [ ] 负责人批准 G3。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 任务卡字段完整、id 唯一 | G3 失败并指出缺字段 |
| 依赖无环；执行计划中依赖只指向更早位置 | G3 失败 |
| 每个场景至少被一个任务覆盖；每个任务至少覆盖一个场景或 chore 理由 | G3 失败，指出未覆盖场景编号 |
| 范围不能是整个仓库；`new_files` 必须在 `scope` 内 | G3 失败，给出实际匹配文件数 |
| 单任务 ≤ 5 文件、变更 ≤ 12 任务 | G3 失败，提示拆分 |
| 必须有验证命令，且形状合法（无 `&&`、`||`、`;`、管道、重定向、命令替换） | G3 失败 |
| 并行批次范围两两不重叠、不碰热点文件 | G3 失败，指出重叠文件/热点文件，建议改顺序或拆分 |
| 每个任务恰好在一个批次里、批次有 why | G3 失败 |
| 执行流程图由插件从执行计划生成 | agent 手写流程图无效，插件以计划为准重新生成 |
| G3 人工批准后冻结（记录哈希） | 直接编辑 `tasks.md` 被拒绝，要求走计划修订 |
| 计划修订人工批准；已开始/已完成任务受保护 | 修订申请被拒绝或部分驳回 |

## 只做引导的部分

- 怎么按竖切拆分、把"薄切片"切多薄。
- 怎么估工时和规模、什么算一个文件。
- 哪些任务该并行、为什么、批次怎么划分最省时间。
- 任务命名、验证组怎么组合。

这些没有代码判定，但批次划分和并行安全会被检查，写 `why` 时要诚实。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 一个任务改十几个文件 | 无法独立验收，出问题定位难 | 拆成多个 ≤ 5 文件的任务 |
| 横切拆分（所有数据层一个任务、所有服务一个任务） | 链路没打通，前几个任务都无法验收 | 按端到端竖切，逐层加厚 |
| 任务卡没写 covers | 场景覆盖出现空洞，追溯矩阵标红 | 每张卡至少覆盖一个场景 |
| 验证命令写 `pnpm test \|\| true` | 验证永远"通过"，没有证据价值 | 去掉兜底，失败就失败 |
| 为了少写几张卡把范围写成 `src/**` | 破坏范围控制，G3 失败 | 精确到目录或文件 |
| 并行批次里两个任务改同一个 Service | 合并冲突，集成检查点失败 | 改成顺序，或把共享部分单独拆出 |
| 并行任务改 `pom.xml` / 路由注册 | 热点文件冲突 | 放进顺序批次 |
| 执行中直接改 `tasks.md` | G3 已冻结，改动无记录 | 用 `flow_request_plan_change` 提交修订 |
| 手写 mermaid 执行图 | 与计划不一致，图会过期 | 让插件生成，只维护执行计划 |

## 正例

```yaml
execution:
  - batch: B1
    mode: sequential
    tasks: [T1, T2]
    why: T1 建续费订单表与实体，T2 在其上实现下单接口；两者都要改 pom.xml 和路由注册，必须顺序。
  - batch: B2
    mode: parallel
    tasks: [T3, T4, T5]
    why: 回调幂等、优惠叠加、到期日计算三块范围互不重叠，都只依赖 B1，可并行。
  - batch: B3
    mode: sequential
    tasks: [T6]
    why: 集成任务：把三块接进续费流程并补端到端测试，依赖 B2 全部完成。
```

## 反例

```yaml
- id: T1
  title: 实现续费
  scope: ["src/**"]
  tests: ["src/**"]
  verify: ["pnpm test || true"]
  depends_on: [T2]
- id: T2
  title: 接续费接口
  scope: ["src/**"]
  depends_on: [T1]
```

问题：范围是整个仓库；验证命令带 `|| true`；没有 covers；T1/T2 依赖成环；没有执行计划。G3 会在多处失败，返回的是可执行的修复提示，而不是一句"不通过"。

## 与其他技能的衔接

- 设计来自 `flow-design`；任务卡范围来自 `flow-context`。
- 批准后进入 S4，由 `flow-orchestrate` 按执行图派发。
- 返工（S5 失败）会生成修复任务，走计划修订。
