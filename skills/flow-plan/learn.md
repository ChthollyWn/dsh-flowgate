# 学习卡：S3 设计拆解（任务与执行计划部分）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

把设计拆成一组能独立完成、能逐个验收的任务卡，每张卡写明覆盖的场景、源码范围、测试范围、新文件、依赖、TDD 要求、验证命令、风险与规模；再把全部任务排成若干批次（顺序或并行）并写清理由，形成执行计划。G3 一次性批准设计、风险与任务清单，之后任务清单冻结，执行图由插件生成。

## 为什么（why）

任务太大，agent 会跑偏，你也没法一步步验收；任务卡没有范围，agent 就会顺手改别的模块；任务卡没有验证命令，完成就是一句空话。把任务拆小并绑定场景与验证命令，让每一步都有明确的靶子和证据；把批次顺序与并行安全提前算清，能避免并行合并冲突和"先做了一堆用不上的底层"。

## 合格标准（criteria）

- 每张任务卡字段完整、覆盖至少一个场景，chore 有理由。
- 场景追溯无遗漏。
- 范围精确、新文件在范围内、单任务 ≤ 5 文件、变更 ≤ 12 任务。
- 每个任务至少一个合法验证命令，`inputs` 声明清楚。
- 执行计划每个任务只出现一次；依赖只指向更早位置；并行批次范围不重叠、不碰热点文件；每个批次有 `why`。
- 执行图由插件生成，没有手写。
- G3 由负责人批准，批准后冻结。

## 对应上游做法（upstream）

- Superpowers 的 writing-plans：把计划写成能逐步执行、每步可验证的形式。
- OpenSpec 的 tasks：任务与需求场景绑定，形成可追溯的变更清单。
- gstack 的 `/plan-eng-review`：动手前审查执行顺序与风险。

FlowGate 的改写：把"任务卡检查、追溯全覆盖、规模上限、执行计划并行安全检查、G3 人工门与批准后冻结"全部放进代码；把"怎么竖切、怎么排批次"作为引导，因为你最了解自己项目的依赖结构。

## 常见反模式（antiPatterns）

- 一个任务改十几个文件，或按数据层/服务层横切。
- 任务卡不写 covers，追溯矩阵留空格。
- 范围写 `src/**`，或新文件不在范围内。
- 验证命令带 `|| true`、`&&`、管道。
- 并行批次两个任务改同一个文件，或并行任务改 `pom.xml` / 路由注册。
- 超过 12 个任务还不拆变更。
- 执行中直接改已冻结的 `tasks.md`，而不是提交计划修订。
- 手写 mermaid 执行图，与实际计划不一致。

## 正例（good）

续费变更拆成 T1 订单表与实体 → T2 下单接口（顺序，因为都要改 `pom.xml` 和路由注册）→ T3 回调幂等、T4 优惠叠加、T5 到期日计算（并行，范围互不重叠、都只依赖 B1）→ T6 集成与端到端测试（顺序）。每个任务 ≤ 5 文件、有 covers 和验证组；G3 一次通过，插件生成 B1→B2→检查点→B3 的执行图。

## 反例（bad）

一张任务卡"实现续费"，范围 `src/**`，验证命令 `pnpm test || true`，没有 covers，和另一个任务互为依赖；没有执行计划。G3 失败：范围过宽、验证命令形状非法、场景未覆盖、依赖成环——每条失败都带修复提示。
