# flow-analysis：只读分析任务

## 何时用

- 负责人问"为什么续费后到期日多了一天""这条调用链怎么走""这两个方案选哪个"这种不要求立刻改代码的问题。
- 大变更开始前需要先调查现状；结论可以转成后续变更的依据。
- 调试中根因复杂、需要先形成带引用的调查报告（补充 `flow-debug`）。

不适用：需要动手修的改代码需求——那建立变更；分析任务的结论要转实施时再建关联变更。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 分析结论 | `.flowgate/changes/<A-id>/analysis.md` | 插件在引用核验通过后写入 |
| 变更台账条目 | `.flowgate/changes/index.md` | 插件写 |
| 调查子 agent 报告 | 会话内回传，plugin 记录耗时/token | 插件派发、只读 |
| 关联变更 | 新建变更时 `relatedTo: "A-xxx"` | agent 创建立项 |

## 步骤（照做即可）

1. **立分析任务。** 调用 `flow_new_change({ kind: "analysis", title, reason })`，编号为 `A-<序号>`。插件用 `restrict` 把可用工具收窄到 read、glob、grep 和 FlowGate 工具——写文件、执行命令都会被拒绝。不要试图用 shell 绕过（本来也没有 shell 权限）。
2. **先明确问题。** 把模糊问题拆成 1–3 个可回答的具体问题，写清"回答到什么程度算够"。例如"到期日多一天"拆成：①续费时到期日从哪个值起算？②时区转换发生在哪几处？③月末（1/31 + 1 个月）怎么处理？
3. **从入口追踪。** 找到功能的入口（Controller / CLI 命令 / 事件监听），顺着调用链读核心字段：字段从哪来、在哪被改写、最终写到哪里。每一步用 `文件:起止行` 记录，关键处附 `quote`。
4. **区分事实与推断。** 事实 = 代码里能直接看到的；推断 = 你根据事实判断的。结论里两者分开写，推断要标"推断"并给出依据，不要用肯定语气写猜测。
5. **大仓库可派调查子 agent。** 用 `flow_investigate({ questions, benefit })` 派只读调查子 agent（默认最多 2 个同时运行），每个只回答一个具体问题，回传带引用的报告；取不到的耗时/token 标"未知"。主会话负责汇总和核验，不要直接采信未核验的结论。
6. **写结论。** 提交 `flow_submit_analysis({ conclusion, proposal, limitations, citations })`：
   - `conclusion`：回答前面列的具体问题，每条带引用；
   - `proposal`：如果建议改，写清改什么、影响范围、怎么验证（不是直接实施）；
   - `limitations`：没查清的部分、假设、取样限制（如实写）；
   - `citations`：`{ file, start_line, end_line, quote }`。
7. **引用会被核验。** 插件读取原文，确认文件与行号存在；提供 `quote` 时它必须出现在这段原文里。核验通过记录哈希并归档；引用不成立会拒绝提交，不要编造行号。
8. **归档与转实施。** 通过后写入 `analysis.md` 并归档，不经过测试、审查、交付阶段。要动手改时用 `flow_new_change({ relatedTo: "A-002" })` 新建关联变更，S1 直接引用分析结论，不重复调查。
9. **结论会被复核。** 被引用的文件之后改动，引用会标"待复核"；如果结论依赖的代码变了，重新核验，不要拿旧结论直接实施。

## 合格标准（可对照检查）

- [ ] 分析任务编号为 `A-xxx`，问题拆成 1–3 个可回答的具体问题。
- [ ] 结论每条都带可核验引用（文件、起止行，必要时 quote）。
- [ ] 事实与推断分开，推断有依据并标注。
- [ ] `limitations` 如实写出没查清的部分，没有假装完整。
- [ ] `proposal` 可执行但不越权：只给建议与验证方式，不直接改代码。
- [ ] 引用核验通过，没有编造行号或原文。
- [ ] 整个任务没有写文件、没有执行命令（工具集已限制）。
- [ ] 转实施时新建关联变更，没有在分析任务里偷偷动手。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 分析任务只能用只读工具（read / glob / grep + FlowGate 工具） | 写文件、执行命令被拒绝 |
| 结论必须带可核验引用（文件存在、行号在范围内、quote 匹配） | `flow_submit_analysis` 被拒绝 |
| 引用记录哈希与时间，文件后来变化标"待复核" | 面板与报告显示待复核 |
| 调查子 agent 默认最多 2 个同时运行、只读 | 超出排队；写操作被拒绝 |
| 取不到的耗时/token 标"未知" | 不用 0 代替 |
| 分析任务不经过测试/审查/交付阶段 | 归档流程固定 |
| 转实施必须新建关联变更 | 分析任务保持只读，不能转成写任务 |

## 只做引导的部分

- 怎样从入口追踪核心字段、停在什么粒度。
- 什么时候可以下结论、什么时候需要更多证据。
- 怎样写 limitation 才有用、怎样组织引用。
- 几个方案怎么比较（不替负责人做决定）。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 在分析任务里改代码 | 工具被限制，且分析结论不可信 | 新建关联变更实施 |
| 结论没有引用 | 无法核验，等于个人意见 | 每条带 `文件:起止行` |
| 编造行号或 quote | 提交被拒，且破坏信任 | 重新读原文再引用 |
| 把推断当事实 | 结论误导后续实施 | 标注"推断"并给依据 |
| 用"可能""大概"下结论 | 不可执行 | 补齐证据或写进 limitations |
| 调查范围无限扩大 | 时间失控 | 先列具体问题，够用就停 |
| 大仓库自己硬读 | 效率低、上下文爆 | 派只读调查子 agent 分头查证 |
| 拿旧结论直接实施 | 引用的代码可能已变 | 重新核验待复核引用 |

## 正例

问题"为什么续费后到期日多一天" → 立 `A-002`。拆成三个问题：到期日起算值、时区转换位置、月末处理。读 `RenewalService.java:80-95`（事实：`expireAt = member.expireAt.plusMonths(months).plusDays(1)`）、`RenewalPolicy.java:40-58`（事实：`plusDays(1)` 与"最后有效日的次日"语义重叠）、`MemberService.java:120-128`（事实：到期日语义定义）。结论：到期日被加了两次一天，推断原因是历史补丁叠加；limitations：未覆盖跨时区部署场景；proposal：删除重复的 `plusDays(1)` 并补月末回归测试。引用核验通过，归档为 `A-002`；随后新建关联变更 `C-004` 修复。

## 反例

agent 在分析任务里尝试写一个临时脚本复现（被拒绝），然后凭记忆写"应该是时区问题，改一下 `LocalDate` 就好"，没有引用、没有事实与推断的区分、limitations 为空。`flow_submit_analysis` 因引用缺失被拒绝；即使补了行号，负责人也无法判断结论是否可信，因为核心代码根本没读。

## 与其他技能的衔接

- 调试中需要只读调查时补充 `flow-debug`。
- 结论转实施：新建关联变更，走 `flow-clarify` → … → `flow-ship`。
- 规则沉淀：分析发现的长期规律可由 `flow-review` / `flow-retro` 提议为规则。
