# 学习卡：只读分析任务

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

对"不改代码"的问题（排查原因、解释调用链、评估方案）立分析任务 `A-xxx`：只能用 read / glob / grep 与 FlowGate 只读工具，先从入口追踪核心字段并记录 `文件:起止行` 引用，事实与推断分开；大仓库可派最多 2 个只读调查子 agent 分头查证。最后用 `flow_submit_analysis` 提交结论、建议、限制与引用，插件核验引用后归档。结论要实施时新建关联变更，不重复调查。

## 为什么（why）

很多问题一开始并不需要改代码，但 agent 容易"边查边改"，把一个调查变成未经批准的实现。分析任务用工具集把"只读"变成硬约束，让你可以放心让它查；要求结论带可核验引用，是因为没有出处的"我觉得是时区问题"无法指导实施，还可能把方向带偏。把结论归档成分析任务，也让下一次实施能直接引用，避免重复调查。

## 合格标准（criteria）

- 问题拆成 1–3 个可回答的具体问题。
- 结论每条带可核验引用（文件、行号，必要时 quote）。
- 事实与推断分开，推断有依据。
- 限制如实写出，没有假装完整。
- 建议可执行但不越权。
- 引用核验通过；文件后续变化标"待复核"。
- 全程只读；转实施走关联变更。

## 对应上游做法（upstream）

- dsh-task-engine 的只读分析契约：用工具集限制分析任务的写能力。
- Superpowers 的 systematic-debugging 中"先找根因"的思路：先建立事实链，再讨论修法。

FlowGate 的改写：把"只读工具集、结论必须带可核验引用、调查子 agent 上限、引用过期待复核、分析不经过测试与交付"交给代码；把"怎么追调用链、什么时候可以下结论"作为引导。

## 常见反模式（antiPatterns）

- 在分析任务里改代码或想跑命令。
- 结论没有引用，或编造行号/quote。
- 把推断当事实，或用"可能""大概"下结论。
- limitations 空着，假装查全了。
- 调查范围无限扩大。
- 大仓库自己硬读，不派调查子 agent。
- 拿旧结论直接实施，不复核引用。

## 正例（good）

`A-002` 查"到期日多一天"：拆成三个问题，读三个文件的对应行并记录引用；事实与推断分开；limitations 写明"未覆盖跨时区部署"；proposal 只建议删除重复的 `plusDays(1)` 并补月末回归测试。引用核验通过后归档，随后新建关联变更 `C-004` 实施修复。

## 反例（bad）

尝试在分析任务里写脚本复现（被拒），随后凭记忆给出"应该是时区问题，改 `LocalDate` 就好"的结论，没有引用、没有事实/推断区分、limitations 为空。提交被拒绝；即便补了行号，负责人也无法判断可信度，因为核心代码没读过。
