# flow-qa：运行验证与冒烟（S5）

## 何时用

- S5：全量测试通过后，验证"服务真的能起来、关键路径真的能用"。
- 普通风险：有运行命令时必需；高风险：必需（日志 + 冒烟）。
- 会话中存在浏览器工具时：按验收场景走一遍并截图（可选，P2）。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 运行证据 | `flow_attach_evidence({ kind: "run" \| "log" \| "screenshot", path, note })` | 标"agent 自述"，高风险 G6 需负责人逐条确认 |
| 完整日志 | 插件记录路径；大输出由插件压缩 | 进入上下文的是摘要 |
| 验收覆盖 | 追溯矩阵 | 每个场景要有通过证据，手工证据标黄 |

## 步骤（照做即可）

1. **确认命令来源。** 运行命令只能是 `project.md` / `config.yaml` 声明的 `run`、`health`、`integration`；不要用临时拼的 `&&` 命令，也不要用生产环境地址。
2. **启动服务。** 用声明的 `run` 命令启动（后台运行），等待就绪：轮询 `health` 命令直到成功或超时；超时不要盲目重试，读启动日志找原因（端口占用、依赖未启动、配置缺失）。
3. **健康检查。** 执行 `commands.health`（例如 `curl -fsS http://localhost:8080/actuator/health`），记录状态码与响应体。
4. **按验收场景冒烟。** 挑覆盖核心路径与最高风险路径的场景，逐条执行：
   - HTTP 服务：请求接口，记录请求、状态码、响应关键字段；
   - CLI：执行真实命令，记录 stdout/stderr 与退出码；
   - 前端/浏览器工具存在时：打开页面按场景操作并截图（每步至少一张关键截图）。
   不要用破坏性操作（删库、真实支付、生产数据）；测试数据放本地或测试库。
5. **采集证据。** 把日志、响应文件、截图用 `flow_attach_evidence` 附上，`note` 写清"哪个场景、命令是什么、期望结果、实际结果"。手工证据会被标为"agent 自述"，高风险时 G6 逐条确认。
6. **清理。** 停止服务，确认没有遗留进程和临时文件；临时脚本不要提交。
7. **失败处理。** 冒烟失败说明变更在 S5 不满足交付条件：S5 失败会生成修复任务回到 S4；不要通过修改测试或跳过场景来"通过 G5"。修复后重新验证并重跑相关冒烟。
8. **覆盖核对。** 逐条对照追溯矩阵：每个验收场景要么有自动化回执、要么有手工证据；纯界面文案、无测试项目这类无法自动化的场景允许手工证据，但要在 G6 由负责人确认。

## 合格标准（可对照检查）

- [ ] 用了 `project.md` / `config.yaml` 声明的 run/health 命令，没有临时拼命令。
- [ ] 服务成功启动，健康检查通过，记录状态码与响应。
- [ ] 按验收场景走完核心路径，每条有请求/输出/截图证据。
- [ ] 证据 note 写清场景、命令、期望、实际。
- [ ] 没有碰生产环境或执行破坏性操作。
- [ ] 服务已停止，没有遗留进程/临时文件。
- [ ] 失败场景已生成修复任务，不是改测试绕过。
- [ ] 风险要求的运行证据齐全（高风险：日志 + 冒烟）。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 运行命令来自声明来源，命令形状合法 | 不合法命令不能执行 |
| G5 按风险要求运行证据（普通风险有运行命令时必需；高风险必需） | G5 失败或标缺失 |
| 验收场景全部有证据（自动化或手工） | G5 失败，列出缺证据场景 |
| 手工证据标"agent 自述" | 不计为自动化证据；高风险 G6 逐条确认 |
| S5 失败 → 生成修复任务回 S4 | 不能直接交付 |
| 浏览器 QA 仅在存在浏览器工具时可用 | 无工具时不能声称"浏览器验证通过" |
| 测试/门禁篡改检测 | 改测试或跳过场景会被标记并进报告 |

## 只做引导的部分

- 冒烟检查怎么设计、挑哪些场景、覆盖多深。
- 启动失败时怎么读日志、怎么定位环境问题。
- 截图与请求记录怎样采集才可信。
- 手工证据与自动化证据的边界判断。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 只跑自动化测试，不启动服务 | 起不来的服务测试全绿也没用 | 按风险做运行验证 |
| 用临时拼的命令或生产 URL | 结果不可复现，可能破坏数据 | 只用声明命令与本地/测试环境 |
| 服务没起来就宣布通过 | 验收场景无运行证据 | 读启动日志排查后再试 |
| 服务跑完不关 | 端口占用、影响后续任务 | 清理进程 |
| 手工截图与场景对不上 | G6 无法确认 | note 写清场景与期望 |
| 冒烟失败就改测试 | 掩盖问题，S5 失去意义 | 生成修复任务回 S4 |
| 没有浏览器工具却声称做了浏览器 QA | 虚假证据，审查会暴露 | 用请求/日志替代或明说未做 |

## 正例

S5：用 `./mvnw -q spring-boot:run` 启动，`curl -fsS http://localhost:8080/actuator/health` 返回 200 且 `{"status":"UP"}`；按 R2.S1 发两次相同流水号回调，第一次 200 且到期日顺延、第二次 200 且到期日不变；按 R3.S2 发错误签名回调返回 401；日志与响应片段用 `flow_attach_evidence` 附上，note 写清每条场景的期望与实际；停止服务后 G5 一次通过。

## 反例

agent 只跑了单元测试就提交 G5；插件提示"声明了运行命令但缺少运行证据"。它临时拼了一个 `curl` 到线上预发环境，触发了运行证据不合法；改为本地启动后服务因端口占用起不来，它没有读日志，直接把验收场景标为"手工确认通过"；G6 时负责人无法确认，交付被退回。

## 与其他技能的衔接

- 前置：`flow-verify` 的自动化证据。
- 失败后回 S4：`flow-debug` + 修复任务（计划修订）。
- 通过后进入 `flow-ship`；终审由 `flow-review` 完成。
