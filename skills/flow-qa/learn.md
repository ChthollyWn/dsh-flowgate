# 学习卡：S5 运行验证与冒烟

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

S5 在自动化验证通过后，用项目声明过的运行命令启动服务、做健康检查，并按验收场景走一遍关键路径（HTTP 请求、CLI 命令、浏览器操作截图），把日志、响应和截图作为运行证据附上；高风险变更必需提供运行证据，普通风险在声明了运行命令时必需。失败则生成修复任务回到 S4。

## 为什么（why）

单元测试证明逻辑对，但不证明服务能起来、依赖能连上、路由和配置没问题。很多交付事故是"测试全绿但一启动就崩"。运行验证用最小代价覆盖这些风险；把证据附上并标清场景，让 G6 的负责人能快速判断"真的可用"，而不是相信一句"我试过了"。

## 合格标准（criteria）

- 使用声明的 run/health 命令，命令形状合法。
- 服务启动成功、健康检查通过，有状态码与响应。
- 核心验收场景逐条冒烟，每条有对应证据。
- 证据 note 写清场景、命令、期望、实际。
- 没有碰生产环境或执行破坏性操作。
- 服务已清理，无遗留进程/临时文件。
- 失败已生成修复任务，没有改测试绕过。

## 对应上游做法（upstream）

- gstack 的 `/qa`：在交付前对真实运行的应用做一轮端到端检查，而不只看单元测试。

FlowGate 的改写：把"运行证据按风险必需、G5 验收场景证据覆盖、手工证据需 G6 确认、浏览器 QA 需要工具存在"写进门禁；把"冒烟怎么设计、采哪些证据"留作引导。

## 常见反模式（antiPatterns）

- 只跑测试不启动服务。
- 用临时拼的命令或生产 URL。
- 服务没起来就宣布通过。
- 跑完不关服务。
- 手工截图与场景对不上。
- 冒烟失败就改测试。
- 没有浏览器工具却声称做过浏览器 QA。

## 正例（good）

启动 Spring Boot 服务，健康检查 200 `UP`；按 R2.S1 连发两次相同回调：第一次顺延、第二次不变；R3.S2 错误签名返回 401；日志和响应片段附证据并写清每条场景的期望与实际；停止服务后 G5 一次通过。

## 反例（bad）

只跑单元测试就提交 G5，被提示缺运行证据；临时拼 curl 访问线上预发环境被拒；本地启动端口占用失败后不读日志，直接把场景标"手工确认通过"；G6 时负责人无法确认，交付退回。
