# flow-context：上下文组织（S2）

## 何时用

- 每次变更进入 S2：为本次变更准备 agent 不靠猜就能工作的上下文。
- 首次进入项目时：`/flow init` 生成 `.flowgate/project.md` 草稿，负责人确认或修订。
- 项目结构/技术栈变化后：更新 `project.md`（负责人维护），再提交 G2。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 项目上下文包 | `.flowgate/project.md` | `/flow init` 生成草稿，负责人维护 |
| 变更级上下文 | `.flowgate/changes/<change-id>/context.md` | agent（G2 后冻结） |
| 命令配置 | `.flowgate/config.yaml` 的 `commands:` | 负责人（可覆盖自动探测） |
| 基线记录 | 插件写入证据库与进行状态 | 插件 |

## 步骤（照做即可）

1. **先读 `project.md`。** 确认技术栈与版本、目录与模块职责、命令（test / build / lint / run / integration / health）、编码约定、禁区、可复用模块清单。每条描述应标"已确认 / 代码推导 / 待确认"；"待确认"的条目要么去读代码核实，要么请负责人确认，不要基于猜测工作。
2. **补全或修订 `project.md`（仅在负责人授权时）。** `/flow init` 的草稿可能漏掉模块或命令；缺命令就写进 `config.yaml` 的 `commands:`。项目确实没有任何测试时，写 `test: none`，G2 会用构建、类型检查和 lint 作为基线（至少要有一项可执行）。
3. **核实命令可执行。** 在项目根目录尝试 `commands.test`（或 build / lint）。识别到 0 个测试时 G2 不通过——命令要能真实跑到测试用例，例如 `./mvnw -B -q test`、`pnpm test`、`pytest -q`。命令不能带 `&&`、`||`、`;`、管道、重定向、命令替换。
4. **写 `context.md`。** 必填四段：
   - **接口约束**：本次涉及的接口路径、请求/响应字段、状态码、错误码、鉴权要求。每条带源码引用 `文件:起止行`。
   - **数据模型**：表/集合/实体、关键字段、约束（唯一索引、外键、默认值）、枚举取值。带引用。
   - **非功能要求**：性能阈值、并发/幂等要求、日志与脱敏、兼容性、回滚要求。
   - **相关模块**：需要复用或修改的模块、可复用的工具函数与服务、明确的禁区（不要碰的模块及原因）。
5. **写明本次不涉及的上下文。** 用一句"本次不改动"列出相邻模块，防止后面的任务顺手扩范围；这也会成为任务卡范围的依据。
6. **基线由插件执行。** 提交 G2 时插件会用声明的命令跑一次全量测试并记录通过 / 失败 / 跳过清单（同一提交号可复用）。基线已有失败时如实记录，不要为了让基线变绿而改测试。
7. **提交 G2。** `flow_submit({ gate: "G2" })`；按失败提示补齐必填段或修命令。G2 是自动门，通过即进入 S3。
8. **引用会过期。** 被引用的源码文件在后续被修改后，引用会标"待复核"；S4 改到这些文件时重新核对并更新引用。

## 合格标准（可对照检查）

- [ ] `context.md` 四段齐全且非空，没有"看着办""按项目惯例"这类空话。
- [ ] 接口约束、数据模型都带 `文件:起止行` 引用，引用真实存在。
- [ ] 声明的测试命令能跑通且至少执行到 1 个测试；或项目确实没测试时 `test: none` + 构建/类型检查/lint 至少一项可执行。
- [ ] 基线已记录（通过、失败、跳过清单）；已有失败已如实列出。
- [ ] 明确了本次可复用模块和禁区。
- [ ] 没有把依赖列表抄成"编码规范"。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| `context.md` 必填段非空 | G2 失败，返回缺失段与示例 |
| 声明的测试命令可执行且至少跑到 1 个测试 | G2 失败，提示"测试命令没有跑到任何测试" |
| `test: none` 时构建 / 类型检查 / lint 至少一项可执行 | G2 失败 |
| 基线已记录；同一提交可复用 | 无基线不能过 G2 |
| 工程骨架变更 C0 允许 0 个测试 | 按 C0 特例通过，但 C0 的 G5 要求跑通至少 1 个测试 |
| 源码引用核验（存在性、行号、quote） | 引用不成立时提交被拒绝 |
| 引用的文件后续变化 | 引用标"待复核"，在面板和报告里提示 |
| 缺少自动化测试 | 自动在风险登记"可维护性"记一条 |
| G2 后冻结 | 写 `context.md` 被拒绝 |

## 只做引导的部分

- 哪些事实值得写进上下文、哪些属于噪音。
- 接口约束和数据模型写多细（够 agent 不猜即可）。
- 怎样描述禁区、怎样列可复用模块。
- 命令探测不到时怎样让负责人快速补全。

背景事实由代码检查兜底，但"够不够清楚"要靠负责人的可读性判断。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 把整个源文件粘进 `context.md` | 浪费 token，关键约束被淹没 | 只摘接口、模型、约束，并给引用 |
| 不写引用 | 结论无法核验，后面可能基于过期事实工作 | 每条事实带 `文件:起止行` |
| 从依赖列表推导编码规范 | 依赖不等于约定，会误导 agent | 约定从代码里读出来并引用 |
| 不告诉 agent 哪些地方不能碰 | 顺手重构相邻模块，越界后返工 | 明确的禁区清单 |
| 为了让基线变绿而跳过/删除测试 | 破坏基线可信度，S5 回归对比失效 | 如实记录已有失败 |
| 测试命令写成 `pnpm test \|\| true` | 永远"通过"，没有证据价值 | 去掉 `\|\| true`，失败就如实失败 |

## 正例

```markdown
## 接口约束
- 回调接口：`POST /api/renewal/callback`，签名头 `X-Signature`，校验见 `src/main/java/com/acme/member/renewal/CallbackController.java:31-57`。
- 成功返回 200 且 body `{"code":0}`；签名错误返回 401；重复回调同样返回 200。

## 数据模型
- `renewal_order(id, member_id, external_txn_id UNIQUE, months, amount_cents, status, paid_at)`，见 `src/main/resources/db/migration/V3__renewal_order.sql:1-14`。
- 到期日 `member.expire_at` 的语义为"最后有效日的次日 00:00"，见 `MemberService.java:120-128`。

## 非功能要求
- 回调处理 p95 < 300ms；同一流水号只处理一次；日志中手机号脱敏。

## 相关模块 / 禁区
- 复用 `SignatureVerifier`、`Money`。
- 禁区：`auth/**`、`MemberBillingJob`（本次不改动，改动需走范围变更）。
```

## 反例

```markdown
## 上下文
本次做续费。后端用 Spring Boot，前端 React。数据库是 MySQL。
测试命令：mvn test（不确定能不能跑）。
注意不要改太多文件。
```

问题：没有接口字段、没有数据模型、没有引用；"不要改太多"不是禁区；测试命令没验证过。G2 会因必填段缺失和命令跑到 0 个测试而失败。

## 与其他技能的衔接

- 上下文会被 `flow-plan` 用来写任务卡的 `scope` / `tests`。
- S4 执行时按任务注入相关片段（`flow-orchestrate`）。
- 引用被改动后的复核在 `flow-verify` 前顺手完成。
