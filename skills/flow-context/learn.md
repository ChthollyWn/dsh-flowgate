# 学习卡：S2 上下文组织

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

把 agent 完成本次变更需要的事实整理成两份文档：项目级 `project.md`（技术栈、目录职责、命令、约定、禁区、可复用模块）和变更级 `context.md`（接口约束、数据模型、非功能要求、相关模块与禁区），每条事实带 `文件:起止行` 源码引用；同时确认测试/构建命令真的可执行，并由插件跑一次基线测试记录通过、失败、跳过清单。

## 为什么（why）

agent 会猜。不告诉它接口字段、数据约束、哪些模块不能碰，它就会编字段、改相邻模块、重复造已有工具——这些错误在 S4 才暴露，修复成本最高。先给足事实再动手，能显著减少返工。基线测试是 S5 回归对比的参照：没有基线，"没有回归"这句话无法证明。上下文带引用则让每个事实可核验，避免基于过期代码做决定。

## 合格标准（criteria）

- `context.md` 四段（接口约束、数据模型、非功能要求、相关模块/禁区）齐全且非空。
- 事实带真实存在的源码引用，引用原文与 `quote` 一致。
- 测试命令能执行并至少跑到 1 个测试；无测试项目用 `test: none` 并提供构建/类型检查/lint 基线。
- 基线记录完整，已有失败如实保留。
- 明确写出复用模块与禁区。
- 编码约定来自代码而不是依赖列表。

## 对应上游做法（upstream）

- OpenSpec `config.yaml` 的 `context` / `rules`：把项目级上下文和规则作为规格的一部分，随变更一起传递。
- gstack 的 `/investigate` 式"先看现场再动手"：上下文不是凭印象写，而是从代码里读出来。

FlowGate 的改写：把"必填段、命令可执行、基线已记录、引用可核验"做成 G2 的机器检查；把"哪些事实值得写、写多细"留给你判断。

## 常见反模式（antiPatterns）

- 把整个源文件粘进上下文，关键约束被淹没。
- 只写"用 Spring Boot/React"这类泛泛描述，没有接口与模型。
- 不写引用，或引用行号早已过期。
- 从依赖列表推导编码规范。
- 不列禁区，agent 顺手改相邻模块。
- 为了让基线变绿而跳过或删除已有失败的测试。
- 测试命令写成 `... || true`，永远"通过"。

## 正例（good）

`context.md` 写清回调接口字段、签名头、返回码与引用；数据模型列出唯一索引和到期日语义；非功能要求给出 p95 阈值与脱敏要求；禁区点名 `auth/**` 和 `MemberBillingJob`。声明的 `./mvnw -B -q test` 真实跑到 12 个测试，基线记录 12 通过 0 失败，G2 一次通过。

## 反例（bad）

`context.md` 只有三段话："本次做续费，后端 Spring Boot，数据库 MySQL，注意别改太多文件。" 没有接口、没有模型、没有引用、没有禁区；测试命令 `mvn test` 未验证，实际跑出 0 个测试。G2 失败两次：必填段缺失、测试命令没跑到任何测试。
