# flow-retro：复盘与规则沉淀（S6 之后）

## 何时用

- 每次交付归档后（低复杂度做简版；中、高、超高做完整版）。
- 想回看一段时间内多个变更的指标（`/flow metrics`、看板）。
- 发现有重复出现的问题，需要沉淀成项目规则时。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 复盘日志 | `.flowgate/retro.md` | **插件追加**，agent 不手写 |
| 指标快照 | `.flowgate/metrics/<change-id>.json` | 插件写 |
| 项目规则 | `.flowgate/rules/<rule-id>.md` | 负责人批准后由插件写入 |
| 规则提议 | 账本 `rule.proposed` 事件 + `RL-n` | agent 用 `flow_propose_rule` 提交 |

## 步骤（照做即可）

1. **拉指标。** 用 `/flow metrics` 或看板读 M-1～M-18。缺失数据标"未知"而不是 0；不要把"未知"当 0 算平均。
2. **逐项解读（不只看好数字）：**
   - M-1 跳步拦截数 / M-2 实际跳步数：门禁有没有漏，agent 最常想跳哪一步；
   - M-3 越界尝试/残留：范围控制效果，越界集中在哪个模块；
   - M-4 虚假完成拦截、M-10 TDD 合规率：验证纪律；
   - M-5 误判率：拦截质量，超过 5% 的规则要复查；
   - M-6 门禁首次通过率：产物质量趋势；
   - M-7 澄清效率 / M-8 需求返工：需求理解质量；
   - M-9 验收覆盖率、M-12 回归失败：交付完整性；
   - M-11 审查发现、M-13 人工负担、M-14 阶段成本、M-15 流程开销、M-17 上下文健康度、M-18 并行效率。
3. **找 1–3 个具体问题。** 限定为"这次真的发生、下次可能再发生"的问题，写清证据（指标 + 账本事件 + 产物位置）。不要泛泛写"沟通不够"。
4. **决定是否沉淀规则。** 审查发现或拦截记录里"真实、已修复、以后还会出现"的问题，用 `flow_propose_rule({ finding, rule, example, scope })` 提交 `RL-n`：
   - `finding`：问题是什么、在哪个文件/场景出现；
   - `rule`：规则内容与触发阶段；
   - `example`：正确写法示例；
   - `scope`：适用范围（路径/任务类型）。
   一次性的误判、还没确认的意见不沉淀。
5. **等负责人决定。** 用 `/flow rule approve RL-n` 或 reject 并写理由；批准后规则写入 `.flowgate/rules/`，之后新建变更自动遵守，进行中变更按冻结契约不受影响。
6. **写复盘结论（交给插件记录）。** 复盘日志由插件自动追加（指标、拦截最多规则、误判、耗时最长阶段、返工原因）。你的贡献是把解读和"下次要改的一个行为"讲清楚，方便负责人查看；不要手写 `.flowgate/retro.md`（受保护文件，写入会被拒绝）。
7. **给出下一个变更的建议。** 从 0 开发时对照路线图：本变更状态、下一个变更是否要调整优先级、MVP 切线是否需要修订（路线图变更走 GR）。
8. **样本小要克制。** 单个变更的指标波动大，不要因为一次数字就改规则；重复出现两次以上再提议。规则库越大维护成本越高。

## 合格标准（可对照检查）

- [ ] 指标从插件读取，缺失值标"未知"。
- [ ] 复盘结论有指标或账本证据支撑，不是印象。
- [ ] 找到 1–3 个具体、可改进的问题。
- [ ] 规则提议针对重复出现的问题，含反例/正例与适用范围。
- [ ] 没有把一次性误判沉淀成规则。
- [ ] 没有手写 `.flowgate/retro.md` 或 `rules/`。
- [ ] 给出下一变更或路线图的明确建议（如适用）。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 指标自动计算（M-1～M-18），取不到标"未知" | 不出现用 0 代替的情况 |
| 复盘日志、指标快照由插件写 | agent 写 `retro.md` 被拒绝 |
| 规则提议必须经负责人批准才生效 | 未批准规则不写入 `rules/`，不影响进行中变更 |
| 进行中的变更按冻结契约执行 | 新规则只影响之后新建的变更 |
| 拦截、审查、返工数据来自账本 | 复盘数据可审计，不能手工编造 |

## 只做引导的部分

- 怎样把指标解读成有意义的问题，而不是罗列数字。
- 什么样的经验值得变成规则、规则写多细。
- 小样本下怎样避免过度反应。
- 下一变更优先级怎么调、MVP 切线要不要动。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 复盘变成指标罗列 | 没有结论，下次照旧 | 挑 1–3 个问题写清证据与改法 |
| 把缺失值当 0 | 平均与趋势被扭曲 | 标"未知"，不参与平均 |
| 把一次性误判写成规则 | 规则库噪音，之后误伤 | 重复出现两次以上再提议 |
| 一次提议十条规则 | 维护成本高，执行不了 | 一次 1–3 条，先跑一段时间 |
| 手写 `retro.md` / `rules/` | 受保护文件，状态与账本不一致 | 用 `flow_propose_rule`，让插件写 |
| 只看单次数字就改流程等级 | 样本太小 | 看多个变更的趋势 |
| 复盘结论"下次注意" | 不可执行 | 落到行为或规则，有可检查的标准 |

## 正例

一次续费变更交付后：M-5 误判率 8%（2/25），集中在"依赖变更需要人工批准"这条规则——复查发现 agent 每次改 `pom.xml` 都被拦，负责人认为这是必要的。M-10 TDD 合规率 100%，M-12 回归 0，但 M-14 显示 S4 耗时占 62%，因为 3 次熔断。结论：①把"依赖变更"的拦截说明里加一行"预期行为，不是故障"；②把本次两次出现的"回调测试漏重复调用"用 `flow_propose_rule` 沉淀为规则。负责人批准后规则生效，下次变更自动提示。

## 反例

复盘只写了一段"整体顺利，测试都过了"，没有指标、没有证据；把 M-5 缺失值写成 0 说"零误判"；一次性把 6 条规则一起提交，负责人无法逐条判断，只能整体拒绝。复盘没有产生任何可执行改进。

## 与其他技能的衔接

- 前置：`flow-ship` 完成交付归档。
- 规则沉淀在 `flow-review` 已经提议过的问题可以直接引用。
- 从 0 开发时结合 `flow-roadmap` 调整后续路线图（改动走 GR）。
