# 学习卡：复盘与规则沉淀

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

交付后读取插件自动计算的 M-1～M-18 指标（缺失标"未知"），结合账本事件找出 1–3 个真实、可能再发生的问题；对重复出现的问题用 `flow_propose_rule` 提交规则提议，由负责人批准后写入项目规则，之后的变更自动遵守。复盘日志与指标快照由插件写，agent 不手写。

## 为什么（why）

同样的错误第二次、第三次出现时，说明流程缺了一条可执行的规则，而不是这次不够小心。复盘把"踩过的坑"从个人记忆变成项目规则，让后面的变更自动避开；指标则让"流程有没有用"可被度量，而不是凭感觉。限定每次只沉淀 1–3 条、且需要重复出现，是为了避免规则库膨胀成噪音。

## 合格标准（criteria）

- 指标来自插件，缺失值标"未知"。
- 结论有指标或账本证据支撑。
- 找到 1–3 个具体可改进的问题。
- 规则提议含问题、规则、正例示例、适用范围。
- 只沉淀重复出现的问题，一次性误判不沉淀。
- 没有手写 `retro.md` / `rules/`。
- 给出下一变更或路线图建议（如适用）。

## 对应上游做法（upstream）

- gstack 的 `/retro`：交付后做结构化复盘，把经验落成下次可执行的改进。

FlowGate 的改写：把指标计算、缺失值处理、复盘日志写入、规则文件管理交给代码；把"怎么解读、沉淀什么"留作引导。规则经人工批准才生效，避免 agent 自我修改流程标准。

## 常见反模式（antiPatterns）

- 复盘变成指标罗列，没有结论。
- 缺失值当 0，扭曲趋势。
- 把一次性误判写成规则。
- 一次提议十条规则，没人维护。
- 手写 `retro.md` / `rules/`。
- 只看单次数字就改流程等级。
- 结论是"下次注意"，不可执行。

## 正例（good）

M-5 误判率 8%（2/25），复查发现"依赖变更转人工"是预期行为，于是在规则说明里加"这是预期，不是故障"；M-14 显示 S4 耗时 62%、3 次熔断，据此把"先复现再改"写进规则提议；两次出现的"回调测试漏重复调用"被沉淀为规则，负责人批准后下次变更自动遵守。

## 反例（bad）

复盘只写"整体顺利，测试都过了"；把 M-5 缺失值写成 0 说"零误判"；一次性提交 6 条规则，负责人无法逐条判断，整体拒绝。复盘没有产生任何可执行改进，下次仍然靠运气。
