# 学习卡：S4 执行（调度部分）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

G3 批准后，主会话按执行图调度：顺序批次逐个执行任务，并行批次同时启动多个子 agent（默认最多 3 个，每个在独立 git worktree），子 agent 只拿任务卡、相关上下文和验证命令，完成后只回传摘要；批次结束由插件合并分支并跑集成检查点，通过后才进入下一批。主会话负责转达问题、处理失败和冲突，不亲自改源码。

## 为什么（why）

一个会话从头做到尾，上下文会膨胀、任务容易串味；顺序错了还会让后面的任务基于未完成的前置工作返工。按执行图派发加上 worktree 隔离，能让并行任务互不干扰；集成检查点把冲突和回归挡在批次边界，而不是在交付时才发现。主会话退到调度位，也让"谁改了哪些文件"有清晰的责任边界。

## 合格标准（criteria）

- 严格按当前可派发批次推进，不跳批次、不提前并行。
- 并行任务数不超过上限，每个任务在正确工作区执行。
- 子 agent 输入自包含，不依赖聊天历史。
- 子 agent 的问题由主会话合并转达，不自行拍板。
- 每个批次都过集成检查点，失败不进下一批。
- 合并冲突、失败任务、中断任务作为待处理项交负责人。
- 主会话没有越权改源码。

## 对应上游做法（upstream）

- Superpowers 的 subagent-driven-development：把任务交给独立上下文的子 agent 执行并回收结构化摘要。
- Superpowers 的 dispatching-parallel-agents：并行任务需要互不依赖且可独立验证。

FlowGate 的改写：把"派发顺序、并行上限、worktree 隔离、集成检查点、子 agent 只读范围"交给宿主代码强制；把"怎样调度、怎样转述问题、怎样处理冲突"作为引导。这样即使模型想偷懒跳批次，代码也不允许。

## 常见反模式（antiPatterns）

- 跳过批次或提前启动并行任务。
- 主会话等不及，自己动手改源码。
- 把聊天结论当上下文塞给子 agent。
- 子 agent 遇到问题自己"合理猜测"而不是停下交回。
- 集成检查点失败还继续下一批。
- 手动合并冲突，不跑检查点。
- 反复重试失败任务，不按系统化排障流程处理。

## 正例（good）

B1 顺序完成 T1→T2 后，`flow_dispatch_next` 启动 B2 的 T3/T4/T5，各在独立 worktree；T4 遇到业务规则空缺，子 agent 停下写问题，主会话合并三个问题问负责人一次；B2 结束检查点合并并跑全量测试，T5 引入的回归被检查点发现，生成顺序修复任务 T5a，修完重跑检查点通过后进入 B3。

## 反例（bad）

主会话为了"快一点"，把 B2 的三个任务和 B3 的集成任务一起启动；三个子 agent 同时改 `RenewalService.java`，worktree 合并时严重冲突；主会话直接 `git merge -X ours` 了事，集成测试失败后仍进入下一批。结果是回归被带到交付阶段，G5 失败，整条流程返工。
