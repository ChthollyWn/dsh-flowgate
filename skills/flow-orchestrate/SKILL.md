# flow-orchestrate：按执行图派发（S4）

## 何时用

- G3 批准后进入 S4，`dispatch` 为 `subagent` 或 `auto` 时：`run: main` 由主会话执行；`run: auto / subagent` 由派发宿主起子 agent（当前版本 `auto` 未按 size 自动路由；需要主会话做的小任务请显式写 `run: main`）。
- 某个任务失败、合并冲突、子 agent 回传需要负责人决定的问题时。

不适用：`dispatch: inline` 时由主会话按顺序自己领取任务（用 `flow_task_start`）。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 执行流程图 | `.flowgate/changes/<id>/execution-plan.md` | 插件生成；节点随状态变色 |
| 进行状态 | `.flowgate/changes/<id>/status.json` | 插件写；记录批次、任务、子 agent、worktree、证据 |
| worktree | `.flowgate/worktrees/<change>/<task>/` | 并行任务各自独立检出；合并后删除 |
| 任务证据 | `.flowgate/state/evidence/<id>.log` + 摘要 | 由 `flow_verify` 产生 |

## 步骤（照做即可）

1. **看当前该派什么。** 调用 `flow_dispatch_next()`。插件返回这次可启动的任务清单：顺序批次 1 个，并行批次最多 `parallel.max_agents` 个（默认 3）。不符合执行图时返回错误和当前可派发的批次——不要手动跳批次。
2. **顺序批次。** 一次只跑一个任务，按批次列出的顺序执行。子 agent 在变更分支 `flowgate/<变更>` 的主工作区工作。
3. **并行批次。** 插件为每个任务建独立 worktree 与分支（`flowgate/<变更>/<任务>`），执行 `parallel.setup` 准备命令，然后同时启动子 agent。主会话不要自己改动任何 worktree。
4. **给子 agent 正确的输入。** 子 agent 由插件启动，只带：任务卡、覆盖的场景、`context.md` 相关片段、验证命令、TDD 要求、最新交接摘要。它没有主会话的聊天历史——不要把"我们刚讨论过"这类上下文依赖交给它。
5. **主会话只做调度，不写源码。** 除非任务卡 `run: main`；否则不要绕过子 agent 自己改文件。子 agent 的写入范围就是任务范围，规则与主 agent 相同。
6. **处理回传。** 子 agent 完成后只回传摘要：改了哪些文件、证据 id、遗留问题、需要负责人决定的问题。插件自动跑任务门（新鲜证据、范围、TDD）和审查；通过后在任务分支提交。
7. **转达问题。** 子 agent 不能提问；它停下并在摘要里写问题。主会话用 `ask_user_question` 问负责人，把答案交回原任务（继续或派新子 agent）。并行批次多个子 agent 同时有问题时，合并成一轮提问。
8. **等批次结束。** 全部任务完成、任务门和审查通过后，插件跑集成检查点：按任务顺序合并分支回变更分支，跑每个任务的验证命令和全量测试（或 `integration` 命令）。
   - 全部通过 → 再调用 `flow_dispatch_next()` 进入下一批。
   - 集成测试失败 → 插件生成一个顺序修复任务（范围只含失败涉及文件），不进入下一批；按任务卡修，不要改测试掩盖。
   - 合并冲突 → 生成待处理项交负责人，不要手工强行合并。
9. **处理失败任务。** 同一任务连续验证失败 3 次会熔断：任务暂停、转人工，并注入系统化排障指引。此时不要反复重试，按 `flow-debug` 走。
10. **中断恢复。** 会话关闭时运行中的任务标"中断"，worktree 与证据保留。重新派发前插件会确认旧子 agent 及其后代已停止；确认不了就保持阻塞转人工，不要抢跑。

## 合格标准（可对照检查）

- [ ] 每次只派当前批次的任务，没有跳批次或同时跑两个批次。
- [ ] 并行批次同时运行的任务数 ≤ `parallel.max_agents`。
- [ ] 每个任务在正确的工作区（顺序任务在主工作区，并行任务在各自 worktree）执行。
- [ ] 子 agent 的输入只有任务卡、相关上下文与验证命令，没有依赖聊天历史的隐性知识。
- [ ] 子 agent 的问题经主会话转达给负责人，没有让子 agent 自行"决定一个合理答案"。
- [ ] 每个批次结束都过了集成检查点，失败时未进入下一批。
- [ ] 合并冲突、失败任务作为待处理项交负责人，没有静默跳过。
- [ ] 主会话没有亲自改任务范围外的源码。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 派发必须符合执行图（批次顺序、批次内顺序） | `flow_dispatch_next` 返回错误与当前可派发批次 |
| 并行上限（默认 3，不超过宿主 `maxActiveSubagents`） | 超出部分排队，不能强启 |
| 并行任务各自独立 worktree 与分支 | 写其他 worktree 或主工作区被拒绝 |
| 每个任务通过任务门与审查后才提交 | 不满足时任务不完成，批次不前进 |
| 集成检查点必须通过才能进入下一批 | 失败时生成顺序修复任务，阻断下一批 |
| 子 agent 只拿到任务卡与相关片段，不带聊天历史 | 由插件构造输入 |
| 子 agent 写入范围 = 任务范围，规则与主 agent 相同 | 越界写入被拒绝 |
| 熔断：同一任务连续失败 3 次 | 暂停任务并转人工 |
| 受管控会话关闭原生委派工具 | `subagent`、`workflow`、`send_message` 不可用，改派被守卫拒绝 |

## 只做引导的部分

- 主会话如何组织调度节奏与提问时机。
- 如何把子 agent 的摘要转述给负责人、如何合并多任务的问题。
- 合并冲突怎么解、失败任务怎么重派。
- 什么时候该把任务改回 `run: main`、什么时候该拆任务。

这些靠你的判断；代码只保证顺序、范围与检查点不被绕过。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 跳过批次、提前启动并行任务 | 依赖未完成，后面全部返工 | 按 `flow_dispatch_next` 返回的批次推进 |
| 让子 agent 直接问负责人 | 子 agent 没有提问工具，会话会卡住 | 子 agent 停下写问题，主会话转达 |
| 把主会话的聊天结论当上下文塞给子 agent | 子 agent 拿不到，行为不可复现 | 把结论写进任务卡或 `context.md` |
| 等不及子 agent，主会话自己把源码改了 | 越权写入、与子 agent 冲突 | 最多处理 `run: main` 的任务 |
| 集成检查点失败还继续下一批 | 失败被带入后续批次，定位困难 | 生成修复任务，修完再过检查点 |
| 手动合并冲突"看着差不多" | 隐藏语义冲突，测试未必覆盖 | 冲突交负责人确认后再合并 |
| 失败任务反复重试 | 触发熔断、浪费时间 | 3 次失败后按 `flow-debug` 排查 |
| 查看子 agent 中间过程并插手 | 破坏隔离，摘要才是契约 | 只处理摘要与待处理项 |

## 正例

执行图 B1（顺序 T1→T2）→ B2（并行 T3/T4/T5）→ CP（集成检查点）→ B3（顺序 T6）。主会话先 `flow_dispatch_next()` 拿到 B1 的 T1，T1 完成后拿到 T2；B2 一次启动 3 个子 agent，各自在 `.flowgate/worktrees/C-003/T3…` 工作；T4 的子 agent 遇到"优惠券能否叠加"停下提问，主会话把 3 个问题合并成一问转达；B2 全部完成后检查点合并并跑全量测试，通过后进入 B3。

## 反例

主会话嫌排队慢，直接 `flow_dispatch_next()` 连发几次，把 B2 的任务在 B1 未完成时启动；两个任务改同一个 `RenewalService.java`，子 agent 互相看不到对方改动；主会话又自己动手"顺手"改了测试。结果：派发被拒绝、越界写入被拦、集成检查点失败——全部返工。

## 与其他技能的衔接

- 执行图来自 `flow-plan`；任务内按 `flow-tdd` 先 RED 后 GREEN。
- 遇到失败用 `flow-debug`；越界与危险动作用 `flow-scope`。
- 每个任务完成前用 `flow-verify` 证明，再进入 `flow-review`。
