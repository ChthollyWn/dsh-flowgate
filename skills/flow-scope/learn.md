# 学习卡：S4 执行（范围控制）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

每次写文件或跑 shell 之前，先核对是否在当前任务卡声明的源码范围、测试范围、新文件与删除/重命名清单内；需要改范围外的东西时，用 `flow_request_scope_change` 说明要加的路径与理由，等负责人批准（`SC-n`）。顺带记录 shell 前后工作区快照，把范围外改动、危险命令、受保护路径写入、测试/CI 篡改都变成可发现的违规。

## 为什么（why）

agent 最自然的失败模式是"顺手"：看到相邻模块命名不顺就重构，发现别的测试红了就改掉，为了过 lint 就放宽规则。这些改动单看都像小事，叠加起来就让审查和回滚失控。范围控制把"该不该现在做"从主观判断变成代码判定；范围变更申请则保留了正当扩展的通道，避免一刀切把合理需求也堵死。

## 合格标准（criteria）

- 写入都命中任务卡范围。
- 删除/重命名已声明，新文件已在 `new_files`。
- 范围外需求走 `SC-n` 并获批后再动手。
- 没用 shell 绕过限制。
- 越界已撤销或获批。
- 危险命令先获批。
- 没写 `.flowgate/` 插件文件、`.git/`、密钥。
- 没改测试、CI、lint、覆盖率配置来让门禁通过。

## 对应上游做法（upstream）

- gstack 的 `/freeze`、`/careful`、`/guard`：把改动范围冻结住，危险动作先停下来确认。
- Superpowers 的 subagent 隔离：每个执行者拿到的边界应当明确且可检查。

FlowGate 的改写：范围不再靠"说好不改"，而是写入前拒绝 + shell 事后检测 + 快照归属（只把 agent 调用期间的改动算给 agent）；危险命令转人工并记账。这样误伤可控（非 agent 改动不算），绕过有痕迹。

## 常见反模式（antiPatterns）

- 顺手重构相邻模块，或"只改一点点"后不断加范围。
- 用 `sed -i`、`mv`、代码生成器绕过写入检查。
- 删除文件不声明，或改了受版本控制文件还不提高风险。
- 改测试/CI 配置让门禁变绿。
- 改 `.flowgate/` 状态文件"修正"状态。
- 危险命令先执行再解释。

## 正例（good）

T3 发现需要改任务范围外的 `RenewalPolicy`。agent 停手，提交 `flow_request_scope_change`，写明路径与理由"R2.S3 的到期日规则由 RenewalPolicy 决定，T3 只读实现无法满足"，负责人批准 `SC-4` 后任务卡范围更新，agent 继续并补测试。整个过程没有越界记录。

## 反例（bad）

agent 觉得 `MemberService` 命名不顺眼直接改，被拒后改用 `sed -i` 批量替换；事后检测记越界并阻止后续写入；它又放宽 lint 规则想蒙混过关，被篡改检测标记。T3 门禁不通过，负责人收到越界与篡改两类待处理项。
