# flow-scope：范围控制（S4，全阶段生效）

## 何时用

- 每次写、删、改名文件之前：核对是否在当前任务卡的 `scope` / `tests` / `new_files` / `changes` 里。
- 想改任务范围外的文件、或发现不改它就做不下去时：申请范围变更。
- 要执行 shell 命令、删除/重命名文件、改依赖清单时。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 任务卡范围 | `.flowgate/changes/<id>/tasks.md` | G3 后冻结；范围变更由插件更新并记账 |
| 范围变更记录 | 账本里的 `scope.requested/approved/rejected` + 任务卡 | 审批用 `/flow scope approve SC-n` |
| 受保护路径 | `.flowgate/`（插件文件与 `state/`）、`.git/`、密钥文件 | agent 一律不能写 |
| 越界检测数据 | `.flowgate/state/snapshots/` | 插件在 shell 前后比对工作区 |

## 步骤（照做即可）

1. **写前核对。** 目标文件是否命中当前任务卡：源码在 `scope`、测试在 `tests`、新文件在 `new_files`。不命中就先停手。
2. **判断类型。** 删除或重命名文件必须在任务卡 `changes` 里声明；未声明会被拒绝，删除受版本控制的文件还会把风险提高为高风险。
3. **范围外需求先申请。** 用 `flow_request_scope_change({ taskId, add: ["路径或目录"], reason: "为什么必须改" })` 提交，生成 `SC-n`：
   - 说明要改什么、为什么现有范围不够、影响哪些场景；
   - 等负责人 `/flow scope approve SC-n` 或 `/flow scope reject SC-n <理由>`；
   - 批准后任务卡范围更新并记账，再动手。
4. **不要用 shell 绕过范围。** `sed -i`、`mv`、`cp`、`echo >`、格式化工具、代码生成器都算写入。插件在每次 shell 调用前后拍快照，期间的范围外改动会立即记为越界，阻止后续写入，直到撤销或获批。
5. **越界后按流程处理。** 立即停手，向负责人说明：改了哪个文件、为什么、如何回退。可用 `git checkout -- <文件>` 撤销范围外改动；确需保留则补范围变更申请。
6. **危险命令会转人工。** `rm -rf`（仓库外或仓库根）、`git push --force`、`git reset --hard`、`git clean -fd`/`-x`、`DROP`/`TRUNCATE`、`curl … | sh`、`chmod -R 777` 等命中触发器：当前动作被拒并生成待处理项，负责人 `/flow risk approve RK-n` 后才可执行一次。
7. **依赖与热点文件。** 改 `package.json` 依赖段、`pom.xml` `<dependencies>`、锁文件、路由注册、依赖注入配置、数据库迁移、共享类型/枚举、多语言资源、CHANGELOG 会命中风险或并行冲突检查；能排进顺序批次就不要塞进并行任务。
8. **插件文件不可写。** `.flowgate/` 里的台账、`status.json`、`execution-plan.md`、`evidence.md`、`review.md`、`report.html`、`state/` 只有插件能写；agent 只能写本阶段允许的产物（`clarify.md`、`proposal.md`、`spec.md`、`context.md`、`design.md`、`risk.md`、`tasks.md`、`analysis.md`）。
9. **非 agent 改动不背锅。** 你在编辑器里手动改的文件不会被记为 agent 越界；面板会提示"检测到非 agent 改动"，G6 会单列确认。agent 不要试图把这类改动混入自己的任务。

## 合格标准（可对照检查）

- [ ] 所有写入都命中任务卡的 `scope` / `tests` / `new_files`。
- [ ] 删除、重命名都在 `changes` 里声明。
- [ ] 范围外需求已走 `SC-n` 申请并获批，没有先斩后奏。
- [ ] 没有用 shell 绕过范围限制。
- [ ] 越界后已撤销或已获批，没有带着未处理越界继续工作。
- [ ] 危险命令在得到负责人批准前没有执行。
- [ ] 没有写 `.flowgate/` 的插件文件、`.git/`、密钥文件。
- [ ] 没有为了让测试变绿而修改测试、CI、lint、覆盖率配置（篡改检测项）。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 阶段写入策略（S0–S3 只能写本阶段产物） | 写源码/测试/配置被拒绝，说明阶段、规则 id、原因与解锁方式 |
| 无活动任务不得改源码（S4 要先领取任务） | 写入被拒绝 |
| 只能写当前任务的范围、测试范围、声明的新文件 | 拒绝，提示"不在 Tn 范围内；确需修改请申请范围变更" |
| 未声明的新文件（防重复造轮子） | 拒绝，提示先查 `project.md` 可复用模块清单 |
| shell 前后快照、范围外改动事后检测 | 记越界并阻止后续写入，直到撤销或获批 |
| 受保护路径 | 写入被拒绝 |
| 删除/重命名未声明 | 拒绝；删除受版本控制文件时风险提高为高风险 |
| 危险命令 | 拒绝当前动作并生成待处理项，人工批准后单次放行 |
| 测试/门禁篡改检测 | 标记，交审查并在 G6 列出 |
| 插件文件只能插件写 | agent 写入被拒绝 |
| 阶段、任务范围、危险命令规则全部可在 `config.yaml` 调整 | 按配置执行 |

## 只做引导的部分

- 怎样判断一个改动是否"真的必要"、能否另立任务。
- 范围变更申请怎么写理由，容易一次通过。
- 越界后怎么沟通与回退。
- 什么时候该提高复杂度或风险，而不是硬塞进当前任务。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 顺手重构相邻模块 | 范围外写入被拒绝；即使放行也会扩大审查面 | 另立任务或申请范围变更 |
| "只改一点点"然后不停加范围 | 每个任务都变成大杂烩，验收失效 | 一项范围变更写清一个目的 |
| 用 `sed -i` / `mv` 绕过写入检查 | 事后检测会记越界并阻止后续写入 | 用正常工具或先申请 |
| 删除文件不声明 | 被拒绝；受版本控制文件还会提高风险 | 写进任务卡 `changes` |
| 改测试/CI 配置让门禁通过 | 篡改检测标记，审查与 G6 都会暴露 | 修实现 |
| 改 `.flowgate/` 状态文件"修正"状态 | 受保护路径，且会造成账本不一致 | 用插件工具/命令 |
| 危险命令先执行再解释 | 已造成不可逆影响 | 先申请，负责人批准后单次执行 |

## 正例

T3 做到一半发现需要改 `RenewalPolicy`（不在 T3 范围）。agent 停手，调用 `flow_request_scope_change({ taskId: "T3", add: ["src/main/java/com/acme/member/renewal/RenewalPolicy.java"], reason: "R2.S3 的到期日规则由 RenewalPolicy 决定，T3 只读实现无法满足" })`，得到 `SC-4`；负责人批准后任务卡范围更新，agent 继续并补了对应测试。

## 反例

T3 的 agent 觉得 `MemberService` 命名不顺眼，直接改；写入被拒绝后改用 `sed -i` 批量替换，事后检测记越界并阻止后续写入；它又把 CI 的 lint 规则改宽松想蒙混过关，篡改检测标记该项。最终 T3 门禁不通过，负责人收到越界与篡改两类待处理项。

## 与其他技能的衔接

- 任务范围来自 `flow-plan`；任务内先跑 `flow-tdd`。
- 越界/失败处理与 `flow-debug` 配合；危险命令判定即风险引擎。
- 审查（`flow-review`）会把范围外改动和篡改项当作发现。
