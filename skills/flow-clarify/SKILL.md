# flow-clarify：需求澄清（S1）

## 何时用

- S0 立项后进入 S1：拿到一句模糊描述（例如"给会员加续费功能"），要把它变成可定稿的需求。
- G1 之后发现需求缺口：不能直接改已冻结的产物，按增量规格（ADDED / MODIFIED / REMOVED）补充，重新过 G1。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 澄清记录 | `.flowgate/changes/<change-id>/clarify.md` | 原始描述、已知事实、六要素、问答记录、假设、未决问题 |
| 变更提案 | `.flowgate/changes/<change-id>/proposal.md` | 为什么做、改什么、影响范围、明确不做什么 |
| 增量规格 | `.flowgate/changes/<change-id>/specs/<capability>/spec.md` | 需求编号 `R<n>`、场景编号 `R<n>.S<m>`、GIVEN/WHEN/THEN |

三个文件都在本阶段可写；G1 批准后全部冻结。

## 步骤（照做即可）

1. **先挖。** 在问第一个问题之前，读与需求相关的代码、已有规格、文档和测试。把读到的内容写成"已知事实"，每条带源码引用：`文件:起止行`（需要时附 quote）。查不到出处的只能写进"假设"。
2. **先复述。** 第一条消息里写两段：①"我理解的需求"（用你自己的话，不超过 5 句）；②"我在项目里发现的事实"（≥ 1 条带引用）。让负责人先纠正理解偏差，再开始提问。
3. **结构化提问。** 用 `ask_user_question` 分轮问：
   - 每轮 ≤ 4 题；
   - 每题 2–4 个选项，推荐项放第一个并标注"（推荐）"；
   - 每题说明"这个回答会改变什么"；
   - 允许负责人自定义回答；
   - 每个问题必须引用已挖到的事实或上一轮回答，禁止模板化提问；
   - 能从代码里查到答案的不要问。
4. **六要素闭合。** 目标、边界（做 / 不做）、角色与权限、验收标准、约束（非功能）、未知与假设。每个要素要么有结论，要么被负责人明确接受为假设。默认最多 4 轮，4 轮后仍不闭合的要素列为"未决问题"，必须由负责人决定，否则 G1 不通过。
5. **写验收场景。** 每条需求至少一个 GIVEN / WHEN / THEN 场景；THEN 必须可测量。模糊词（快、友好、适当、尽量、等等、良好、合理）会被检查失败，改写成阈值或可观察结果，例如"p95 < 300ms""按钮显示'马上抢购'""重复回调后到期日不变且返回 HTTP 200"。
6. **写 `clarify.md`。** 结构：原始描述 / 已知事实（带引用）/ 六要素表（要素、结论、来源、状态）/ 问答记录（问题、选项、回答、这个回答改变了什么）/ 已接受的假设 / 未决问题（必须为 0 才能过 G1）。
7. **写 `proposal.md` 和增量规格。** 提案写清为什么、改什么、影响哪些模块、明确不做什么；增量规格用 `## ADDED Requirements`、`## MODIFIED Requirements`、`## REMOVED Requirements`，需求编号 `R1…Rn`、场景 `R<n>.S<m>`。MODIFIED 要写出修改后的完整需求并注明改了什么；REMOVED 写移除原因和迁移方式。
8. **自检后提交。** 对照下方"合格标准"逐项打勾，然后 `flow_submit({ gate: "G1" })`。失败时按 `failures[].hint` 修，不要绕过检查。
9. **给一页摘要。** 通过后给负责人一页"最终需求摘要"（目标、关键决定、场景清单、明确不做、假设与风险），然后结束本轮等待 `/flow approve G1` 或退回意见。
10. **G1 之后。** 产物冻结；需求变化只能写增量并重新过 G1，不要直接改 `proposal.md` / `spec.md` / `clarify.md`。

## 合格标准（可对照检查）

- [ ] 第一条消息里复述了需求，且至少引用一处项目事实（`文件:起止行`）。
- [ ] `clarify.md` 六要素齐全，每项有结论或已接受的假设。
- [ ] 未决问题为 0。
- [ ] 每条需求至少一个场景；场景使用 GIVEN / WHEN / THEN。
- [ ] THEN 中没有未量化的模糊词。
- [ ] "不做"清单非空，并写了为什么不做。
- [ ] 问答记录每行都有"这个回答改变了什么"。
- [ ] 增量规格格式合法，编号连续，MODIFIED / REMOVED 写明迁移方式。
- [ ] 事实都有可核验的源码引用；引用不存在或 `quote` 不匹配会被拒绝。
- [ ] 负责人已批准 G1。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 六要素闭合、未决问题为 0 | G1 失败，返回缺失的要素和示例写法 |
| 每条需求 ≥ 1 个场景、场景格式合法 | G1 失败并指出缺少场景的需求编号 |
| THEN 中出现模糊词 | G1 失败，提示"改为可测量阈值，例如 p95 < 300ms" |
| "不做"清单为空 | G1 失败 |
| 源码引用不存在、行号越界或 quote 不匹配 | 提交被拒绝，要求重新核对 |
| 事实没有引用 | 只能算假设，G1 按"六要素未闭合"处理 |
| G1 人工批准 | `flow_submit` 通过后停在等待负责人，agent 不能自行放行 |
| G1 后冻结 | 写 `clarify.md` / `proposal.md` / `spec.md` 被拒绝，提示走增量 |
| 澄清轮数上限（默认 4） | 超过轮数仍在提问会被提示收敛为"未决问题"交负责人决定 |
| 问答记账 | `ask_user_question` 的问答自动写入账本与 `clarify.md`；自动落账的「改变说明」是占位符（`（待补充）`），G1 前必须编辑 `clarify.md` 补全每一行的「这个回答改变了什么」，占位符会被 G1 拒绝 |

## 只做引导的部分

- 先挖什么：从哪里读、读多深、哪些历史讨论值得翻。
- 怎样设计选项：什么时候给 2 个、什么时候给 4 个，推荐项怎么定。
- 怎样复述需求、怎样组织问题顺序（先目标后边界，再角色与约束）。
- 怎样把"快""友好"这类模糊表达转成可测量的描述。

这些没有代码判定，靠负责人判断你是否真的理解了需求。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 拿到题就开写 | 需求没定稿就进 S3 就会返工，G1 也会被打回 | 先挖再问，复述后等确认 |
| 问代码里能查到的事 | 浪费负责人的时间，暴露没读项目 | 先读代码，把答案写进"已知事实" |
| 模板化提问 | 问题与项目无关，负责人只能泛泛回答 | 每题引用一处事实或上一轮回答 |
| THEN 写"续费要快" | 不可验证，S5 无法证明做到 | 改成"p95 < 300ms"这类阈值 |
| 六要素里"不做"空着 | 边界不清，范围膨胀 | 明确写出不做什么及理由 |
| 在 S1 里设计实现方案 | 跳过需求确认，方案错误会放大 | 把"怎么做"留到 S3，S1 只写需求 |
| 未决问题挂着不处理 | G1 不通过，后面全部卡住 | 每项要么被负责人决定，要么被接受为假设 |

## 正例

```markdown
### Requirement: R2 续费回调幂等
系统 SHALL 对同一支付流水号的续费回调只处理一次。

#### Scenario: R2.S1 重复回调
- GIVEN 会员 A 的续费订单已因流水号 P1 成功处理
- WHEN 支付平台再次推送流水号 P1 的成功回调
- THEN 会员 A 的到期日不变，接口返回 HTTP 200

#### Scenario: R2.S2 首次回调
- GIVEN 会员 A 的续费订单已创建、流水号 P1 尚未处理
- WHEN 支付平台推送流水号 P1 的成功回调
- THEN 到期日按购买月数顺延，且只顺延一次
```

配套问答记录示例：问题"回调重复时返回 200 还是 409？答 200 会让支付平台停止重试，答 409 会继续重试——这个回答会决定幂等表的保留策略"，负责人选择"200，并保留 90 天幂等记录"。

## 反例

```markdown
### Requirement: R2 续费
系统应该支持续费，体验要快，尽量友好。

#### Scenario: 续费
- GIVEN 会员
- WHEN 续费
- THEN 尽快到期
```

问题：没有流水号与幂等语义；THEN 里"尽快"是模糊词；场景缺少可观察的返回值；需求没有边界。G1 会指出模糊词并给出可测写法示例。

## 与其他技能的衔接

- 通过 G1 后进入 `flow-context`（S2）。
- 需求缺口会触发回退到 S1，走本技能的增量流程。
- 澄清中发现的只读疑问（如"现在到期日怎么算的"）可以立 `flow-analysis` 分析任务，结论转成关联变更，不重复调查。
