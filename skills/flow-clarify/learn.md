# 学习卡：S1 需求澄清

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

在提第一个问题之前先读项目：相关代码、已有规格、文档和测试，把读到的内容写成带 `文件:起止行` 引用的事实，并先复述"我理解的需求"。然后用 `ask_user_question` 分轮提问（每轮 ≤ 4 题、每题 2–4 个选项、推荐项在前、说明"这个回答会改变什么"），把目标、边界、角色与权限、验收标准、非功能约束、未知与假设六要素问到闭合，最后产出 `clarify.md`、`proposal.md` 和带 GIVEN/WHEN/THEN 场景的增量规格，交负责人定稿（G1）。

## 为什么（why）

agent 拿到模糊描述直接开写，是返工的最大来源：需求理解偏差要到 S4 甚至 S5 才暴露，代价最高。先把需求和验收标准钉死，后面每个任务、每条证据都有可对照的靶子；把"不做"写清楚，才能挡住顺手扩大范围。G1 让负责人在写代码之前只确认一次需求，而不是在交付时才发现做错。

## 合格标准（criteria）

- 第一条消息复述需求并引用至少一处项目事实。
- 六要素齐全，未决问题为 0，每项要么有结论要么被接受为假设。
- 每条需求至少一个 GIVEN/WHEN/THEN 场景，THEN 可测量、无模糊词。
- "不做"清单非空且写了理由。
- 问答记录每行有"这个回答改变了什么"。
- 增量规格 ADDED / MODIFIED / REMOVED 格式合法，编号连续。
- 事实带可核验引用；假设与事实分开。
- 负责人批准 G1，之后产物冻结。

## 对应上游做法（upstream）

- Superpowers 的 brainstorming：先发散再收敛，避免拿到题就动手。官方 v7.0.1 发布说明提到，brainstorming 改版前测试中 agent 24 次运行有 24 次跳过设计直接开工——这正是"靠提示词约束不住"的证据，所以 G1 必须是代码强制的人工门。
- gstack 的 `/office-hours`、`/spec`：先访谈目标与边界，再形成规格。
- OpenSpec 的 propose / explore 与 `specs/` 约定：需求与场景用可归档的增量规格表达。

FlowGate 的改写：把"六要素闭合、场景可测试、未决为 0、事实带引用"变成 G1 的机器检查，把"先挖后问、选项设计、复述"保留为引导，因为你/负责人的判断无法被代码代替。

## 常见反模式（antiPatterns）

- 拿到题就开写，跳过澄清。
- 问代码里能查到答案的问题，或问与项目无关的模板问题。
- THEN 写"快""友好""尽量"，无法验证。
- "不做"清单空着，范围没有边界。
- 在 S1 里设计实现方案，把需求问题变成技术选择。
- 未决问题挂着不处理，或把假设混进"已知事实"。
- G1 通过后直接改冻结产物，而不是写增量。

## 正例（good）

需求"加会员续费"：agent 先读 `RenewalService.java:80-95`、`Member.java` 和已有 `specs/member/spec.md`，第一条消息复述需求并列出 3 条带引用的事实；两轮共 5 个问题，每个都有选项和影响说明；产出 `clarify.md`（六要素全闭合）、`proposal.md` 和 R2/R3 两条需求共 5 个 GIVEN/WHEN/THEN 场景；G1 一次通过。

## 反例（bad）

需求"加会员续费"：agent 直接写 `RenewalService` 的实现，然后补一句话"续费功能已完成，测试通过"。没有澄清记录、没有场景、没有"不做"清单；即使它最后写对了，G1 也会因为六要素缺失和场景缺失而失败，并且这个变更可能在 S4 被范围规则拦下——因为没有任务卡声明它要改的这些文件。
