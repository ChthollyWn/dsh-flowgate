# flow-design：设计（S3）

## 何时用

- 每次变更进入 S3：为 `flow-plan` 提供可拆解的技术方案。
- 复杂度提高、或执行中发现需要跨模块改动时：回到 S3 补 `design.md` 与执行计划。
- 高风险变更：必须先有回滚方案。

## 产物路径

| 产物 | 路径 | 可见性 |
|---|---|---|
| 设计文档 | `.flowgate/changes/<change-id>/design.md` | agent 写，G3 后冻结 |
| 风险登记 | `.flowgate/changes/<change-id>/risk.md` | agent 写，G3 后冻结 |
| 风险触发器 | `.flowgate/config.yaml` 的 `triggers:` | 负责人维护 |

## 步骤（照做即可）

1. **收齐约束。** 从 `clarify.md`、`context.md`、`project.md` 里列出：必须实现的场景（R 编号）、不能碰的禁区、非功能阈值、已有可复用模块、部署与数据迁移限制。
2. **至少提出 2 个方案（高复杂度 2–3 个）。** 包括一个"最小改动"方案。方案不是凑数：每个要写清改动面、优点、缺点、风险、失效模式、回滚方式。
3. **对比并推荐。** 用一张表按"符合需求程度 / 实现成本 / 风险 / 可回滚性 / 可测试性"对比，明确选哪个、为什么，以及不选的那个在什么条件下值得重新考虑。
4. **写数据流。** 从入口（页面/接口/命令）到业务逻辑、存储、返回，逐步写清每一步的输入输出和失败路径；标出事务边界与幂等点。
5. **写错误处理。** 一张表：失败场景（参数非法、依赖超时、重复请求、并发冲突、部分成功）→ 怎么处理 → 返回什么 → 如何验证。不要只写"异常时回滚"。
6. **高风险写回滚方案。** 数据迁移要写前进与回退脚本；接口变更要写兼容期与开关；外部依赖要写降级。回滚方案必须能被执行，不能是"联系运维"。
7. **列新增依赖与热点文件。** 需要新增依赖、改路由注册、改依赖注入配置、改数据库迁移或共享类型时逐条列出——这些工作会被排进顺序批次，不能塞进并行批次。
8. **填 `risk.md`。** 五类：安全、性能、成本、合规、可维护性。每类写等级（无 / 低 / 中 / 高）、理由、缓解措施、验证方式、是否需要人工接管；等级为"无"也要写一句理由（例如"不新增外部调用，无新增成本"）。高风险项由负责人在 G3 逐项确认。
9. **超高超大复杂度额外写架构边界。** 模块边界、影响范围、取舍（为什么不做另一条路）、迁移路径。
10. **提交 G3。** 调用 `flow_submit({ gate: "G3" })`；设计、风险、任务卡一起被检查，批准后全部冻结。

## 合格标准（可对照检查）

- [ ] 方案对比段存在，2–3 个方案是真方案（有取舍），不是稻草人。
- [ ] 推荐方案与理由明确，并写了什么情况下重新考虑落选方案。
- [ ] 数据流覆盖入口到存储到返回，标出事务/幂等点。
- [ ] 错误处理表覆盖至少：参数非法、依赖失败、重复请求、并发冲突。
- [ ] 高风险有可执行的回滚方案。
- [ ] `risk.md` 五类齐全，每类有等级、理由、缓解、验证方式；"无"也写了理由。
- [ ] 新增依赖、热点文件逐条列出，已考虑放进顺序批次。
- [ ] 设计与需求场景对得上：设计里每个关键决定能指向它服务的场景编号。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 中复杂度在有多个可行方案时、高/超高复杂度必须有 `design.md` | G3 失败，提示缺设计文档 |
| 方案对比段存在（至少 2 个方案 + 推荐） | G3 失败 |
| `risk.md` 五类齐全，每类有等级与理由 | G3 失败，指出缺失类别 |
| 高风险必须有回滚方案 | G3 失败 |
| G3 人工批准 | 通过检查后停在等待负责人，agent 不能自行放行 |
| G3 后冻结 | 写 `design.md` / `risk.md` 被拒绝，改动走计划修订或返工流程 |
| 风险等级与复杂度只能人工降低 | `/flow risk-level`、`/flow complexity` 由负责人执行 |

## 只做引导的部分

- 怎样设计有意义的方案对比（而不是"方案 A：这样做；方案 B：不这样做"）。
- 怎样评估成本、风险、可逆性。
- 回滚方案写到什么程度算可执行。
- 架构边界怎么切。

这些没有唯一正确答案，由你在文档里陈述理由，负责人判断。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 只写一个方案 | 没有对比就无法证明选择合理，G3 失败 | 至少再给一个真实可行的方案 |
| 稻草人对比 | 陪跑方案明显不可行，等于没对比 | 每个方案都写清代价与适用前提 |
| 设计写成了代码走读 | 没有决策信息，任务拆解无据可依 | 写决策、边界、数据流、错误处理 |
| 风险五类都填"无" | 等于没做风险识别，G3 失败 | 每类写理由，确实无风险就写为什么 |
| 高风险没有回滚方案 | 出事无法收场 | 写可执行的回滚步骤与验证 |
| 在并行任务里改路由注册/依赖清单 | 与热点文件规则冲突，G3 失败 | 单独排进顺序批次 |
| 设计里悄悄扩大范围 | 后续任务卡超出原需求 | 每个决定回指场景编号，多做的部分单独立项 |

## 正例

```markdown
## 方案对比
| 方案 | 做法 | 成本 | 风险 | 回滚 | 结论 |
|---|---|---|---|---|---|
| A 唯一索引 + 先查后写 | 依赖 DB 唯一索引兜底并发 | 低 | 中：需处理唯一键冲突 | 删索引即可 | 推荐 |
| B 分布式锁 | Redis 锁串行化回调 | 高 | 高：新增基础设施 | 需运维配合 | 不选 |

推荐 A：当前单库部署，唯一索引能覆盖并发回调；若将来多库分片，重新评估 B。
## 错误处理
| 场景 | 处理 | 返回 | 验证 |
|---|---|---|---|
| 签名错误 | 拒绝并记录 | 401 | R3.S2 测试 |
| 重复流水号 | 按已处理返回 | 200 | R2.S1 测试 |
## 回滚方案
关掉回调开关 `renewal.callback.enabled=false`，删 `uk_renewal_txn` 索引；已处理订单保留，不影响历史数据。
```

## 反例

```markdown
## 设计
用唯一索引做幂等，在 Service 里先查再写。异常时回滚。风险：无。
```

问题：只有一个方案（G3 失败）；没有数据流和错误处理；风险五类缺失；没有回滚方案。即使实现正确也无法通过 G3，因为负责人无法判断选择是否合理。

## 与其他技能的衔接

- 设计完成后交给 `flow-plan` 拆任务卡和执行计划。
- `risk.md` 里的高风险项在 G3 由负责人逐项确认；S4–S6 由风险触发器继续兜底（`flow-scope`）。
