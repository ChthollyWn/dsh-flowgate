# 学习卡：S4 执行（系统化排障）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

验证失败时先停下来复现，读完整失败日志，一次只验证一个假设，定位到最小根因；为 bug 补一个当前失败的回归测试，再修根因（只改任务范围内），拿到新鲜 GREEN 并记录根因。同一任务连续失败 3 次会熔断，任务暂停转人工，并注入系统化排障指引。

## 为什么（why）

失败后立刻改代码、同时改几处、反复试错，是把时间花在碰运气上；更糟的是为了变绿去改测试或吞异常，把 bug 藏起来。先复现再定位，让每次修改都有依据；补回归测试保证同一问题不会再回来。熔断机制在态度层面拦住"再试一次就好了"的冲动——连续 3 次失败说明当前假设有问题，需要换方法或找人。

## 合格标准（criteria）

- 有可复现结论（稳定/偶发/无法复现）和完整日志依据。
- 每次只验证一个假设，能说清"如果是它应该看到什么"。
- 根因明确，修复针对根因。
- 有先失败后通过的回归测试。
- 修复范围在任务卡内；范围外根因已申请。
- 没有改测试、吞异常、加掩盖性重试。
- 连续失败未超过 3 次；熔断后按指引交回负责人。

## 对应上游做法（upstream）

- Superpowers 的 systematic-debugging：复现 → 定位根因 → 修复 → 回归，禁止靠猜测修改。
- gstack 的 `/investigate`：先建立事实与证据链，再下结论。

FlowGate 的改写：把"连续失败 3 次熔断、测试篡改检测、范围限制、修复后必须新鲜 GREEN"写进代码；把"怎么复现、怎么排序假设、什么时候立分析任务"留作引导。

## 常见反模式（antiPatterns）

- 不看日志直接猜、同时改多处。
- 把测试改成能过、删断言、跳过用例。
- 加 try/catch 吞异常或重试掩盖问题。
- 修完不补回归测试。
- 范围外顺手修。
- 熔断后继续反复试错。
- 把需求理解错误当成 bug 硬修。

## 正例（good）

偶发失败：先单跑 10 次复现 3 次；日志显示失败时到期日多一天；假设时区换算重复加天，写回归测试（当前失败）；定位到 `addMonths` 后调用方又加一天；删除重复加天并改用 `Clock`；GREEN 且全量无回归；证据 note 记录根因。整个过程 2 次失败内解决，没有触发熔断。

## 反例（bad）

失败后连续盲改 5 个文件，第 3 次失败被熔断；继续尝试 `@Disabled` 掉测试，被篡改检测标记；把断言从精确值改成"不为空"后 GREEN，但 R2 实际未实现，S5 回归失败、审查指出虚假完成。
