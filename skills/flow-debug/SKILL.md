# flow-debug：系统化排障（S4）

## 何时用

- `flow_verify` 失败，且不是明显的笔误或环境问题。
- 行为与验收场景不符、测试时过时不过、集成检查点失败。
- 同一任务连续失败 2 次时提前进入本流程，避免第 3 次触发熔断。

不适用：需求没想清楚导致的"失败"——那是需求缺口，走 S1 增量，不是 debug。

## 产物路径

| 产物 | 路径 | 说明 |
|---|---|---|
| 失败回执 | `.flowgate/state/evidence/<id>.log` | 完整输出在日志，摘要进上下文 |
| 根因说明 | `flow_attach_evidence` 的 `note`，或分析任务 `analysis.md` | 复杂根因可立只读分析任务 |
| 回归测试 | 任务卡 `tests` 范围 | 修复必须配一个能复现原问题的测试 |

## 步骤（照做即可）

1. **停下来，先复现。** 不看实现猜原因；用最小命令复现：单跑失败用例、放大失败日志、构造最小输入。记录"稳定复现 / 偶发 / 无法复现"三种结论之一。
2. **读完整证据。** RED/失败回执里有失败用例名和首行错误，完整日志在 `.flowgate/state/evidence/`。先读日志，别只看摘要。
3. **一次只验证一个假设。** 列出 2–3 个可能根因，按最可能排序；对每个根因写"如果是它，应该看到什么"，然后用一次实验验证。不要同时改多处再跑。
4. **定位到最小原因。** 用 `git log` / `git diff` / 最近改动定位引入点；必要时二分（`git bisect`）或临时加日志/断言。临时调试代码必须在任务完成前撤掉，或已声明在范围内。
5. **先写复现测试。** 为这个 bug 补一个当前失败的回归测试（在任务卡 `tests` 范围内），确认它在旧代码上失败、在修复后通过。
6. **修根因，不修症状。** 只改任务卡 `scope` 内的源码；不改断言、不跳过测试、不吞异常、不加"重试三次"掩盖问题。如果根因在任务范围外，用 `flow_request_scope_change` 申请，不要偷偷改。
7. **跑验证。** `flow_verify` 拿到 GREEN；如果这是新补的测试，同时确认全套相关测试没有回归。
8. **记录根因。** 用 `flow_attach_evidence` 附一条"根因 + 修复方式 + 验证证据"，或把复杂调查立为只读分析任务并把结论关联到变更。
9. **连续失败熔断。** 同一任务验证连续失败 3 次 → 任务暂停并转人工，插件注入系统化排障指引。此时不要继续试错：向负责人说明已排除的假设、当前怀疑的根因、需要什么信息或决定。
10. **修改共享假设时。** 如果发现是 `context.md` 或需求理解错了，不要将错就错：回到对应阶段补增量（S1）或更新上下文（S2 后由负责人处理），不要修改测试去迁就错误实现。

## 合格标准（可对照检查）

- [ ] 先有可复现结论，再动手改代码。
- [ ] 失败证据读到了日志（不是只看摘要）。
- [ ] 每次只验证一个假设，有"如果是它应该看到什么"的记录。
- [ ] 根因写明，不是"改了改就好了"。
- [ ] 有能复现原问题的回归测试，且在旧行为下失败、修复后通过。
- [ ] 修复只改任务范围；范围外根因已申请范围变更。
- [ ] 没有删除/跳过测试、弱化断言、吞异常、加掩盖性重试。
- [ ] GREEN 回执新鲜；连续失败未超过 3 次。
- [ ] 根因说明已记录（证据 note 或分析任务）。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 连续失败 3 次熔断 | 任务暂停并转人工，注入系统化排障指引 |
| 验证回执由 `flow_verify` 产生且新鲜 | 任务门不接受自跑结果 |
| 测试篡改检测（删除、跳过、删断言） | 标记交审查并在 G6 列出 |
| 范围外写入 | 拒绝，要求走范围变更申请 |
| 修复后必须有新鲜 GREEN 才能 `flow_task_done` | 拒绝完成 |
| 熔断后继续试错 | 写操作仍受任务状态限制 |

## 只做引导的部分

- 怎么设计最小复现、怎么选假设顺序。
- 什么时候该二分、什么时候该读源码。
- 什么时候停下来问负责人、什么时候立分析任务。
- 怎么记录根因最有用。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 不看日志直接猜 | 改错方向，浪费轮次 | 先读完整输出再假设 |
| 同时改多处再跑 | 不知道是哪处生效，可能引入新问题 | 一次只验证一个假设 |
| 把测试改成能过 | 症状被掩盖，回归继续存在 | 修实现，保留测试强度 |
| 加 try/catch 吞异常或"重试三次" | 把崩溃变成静默错误 | 查根因，明确失败行为 |
| 范围外顺手修 | 越界、破坏任务边界 | 申请范围变更或另立任务 |
| 连续失败仍反复试 | 第 3 次熔断，浪费时间 | 提前按系统化流程排障 |
| 修完不补回归测试 | 同类问题会再次出现 | 补一个复现测试 |
| 把需求错误当 bug 修 | 实现跟着错误需求走 | 回 S1 写增量 |

## 正例

测试 `RenewalCallbackTest` 偶发失败。agent 先单跑 10 次复现（3 次失败），读日志发现失败时到期日多一天；假设是时区换算重复加一天，写一个断言到期日精确值的回归测试（当前失败）；定位到 `RenewalPolicy.addMonths` 用了 `LocalDate.plusMonths` 后又在调用方加一天；删掉重复加天并改用时区安全的 `Clock`；`flow_verify` GREEN，全套回归无新增失败；证据 note 记录根因。

## 反例

测试失败后 agent 连续改了 5 个文件、每改一次就跑一次全量测试，第三次失败后被熔断；它继续尝试 `@Disabled` 掉失败测试，被篡改检测标记；最后把断言从"到期日等于 X"改成"到期日不为空"，GREEN 了但需求 R2 实际没有实现，S5 回归与审查同时失败。

## 与其他技能的衔接

- 复现与验证用 `flow-verify`；需要只读调查时立 `flow-analysis` 任务。
- 范围外根因用 `flow-scope` 申请。
- 修完进入 `flow-review`。
