# flow-roadmap：项目路线图（从 0 开发）

## 何时用

- 空仓库（除 README、LICENSE 外没有源码），或负责人明确说"这是一个新项目"。
- 已有一条冻结的路线图，要增删能力、调整 MVP 切线或依赖 —— 这属于路线图增量，重新过 GR。

不适用：已有代码的项目加功能，直接从 S0 立项，用不到本技能。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 项目级澄清记录 | `.flowgate/project-clarify.md` | agent（GR 后冻结） |
| 路线图 | `.flowgate/roadmap.md` | agent（GR 后冻结；"状态"列只有插件能写） |
| 项目上下文包 | `.flowgate/project.md` | `/flow init` 生成草稿，负责人维护 |

## 步骤（照做即可）

1. **先挖后问。** 空仓库没有代码可挖时，先读负责人给的材料（需求文档、竞品链接、草图、口头描述的要点），把读到的东西列为"已知事实"；查不到来源的内容写进"假设"，不要冒充事实。
2. **项目级澄清。** 六要素各写一条结论：目标用户与核心价值、核心流程（3–5 步）、MVP 做什么、MVP 不做什么、技术栈与部署方式、非功能要求与约束。用 `ask_user_question` 提问，每轮 ≤ 4 题，每题 2–4 个选项、推荐项放第一并标注、写清"这个回答会改变什么"。
3. **按能力拆变更。** 一个变更 = 一个能独立验收的能力，例如"用户与鉴权""会员""续费""后台报表"。拆完检查：每个 MVP 能力都有归属变更；预计任务数 ≤ 12；依赖关系指向一个方向（无环）；先做能证明工程可跑的骨架。
4. **确定 MVP 切线。** 在路线图顶部用一句话写明切线：哪些变更在 MVP 内、哪些在切线外。切线不是"以后再说"，而是明确排除并写理由。
5. **C0 固定为工程骨架。** 目录结构、构建、测试框架、lint、CI、至少一个冒烟测试。C0 的 G2 允许 0 个测试（它就是来建测试的），但 C0 的 G5 要求测试框架真实跑通至少一个测试。
6. **写 `roadmap.md`。** 使用 03 文档 §9.7 的表格：变更 / 能力 / 一句话目标 / 验收要点 / 依赖 / 预计任务数 / MVP / 状态。验收要点必须能被验证，不要写"体验流畅"。
7. **提交 GR。** 调用 `flow_submit({ gate: "GR" })`。检查失败时按返回的 `failures[].hint` 逐条修，不要绕过。
8. **等人工批准。** 通过后你会看到 `awaiting: "owner"`；结束本轮并告诉负责人用 `/flow approve GR` 或面板批准。不要在等待期间开始写代码。
9. **放宽后立项。** 用 `flow_new_change({ fromRoadmap: "C0" })` 从路线图条目创建立项，路线图里的目标、验收要点和项目级决定会自动带入；S1 只补这个能力的细节。
10. **推进路线图。** 每个变更交付后，插件更新"状态"列；`/flow roadmap` 查看进度（M-16）。

## 合格标准（可对照检查）

- [ ] `project-clarify.md` 六要素齐全，每个要素有结论或负责人已接受的假设。
- [ ] 每个变更对应一个可独立验收的能力，一句话目标和验收要点都不为空。
- [ ] 依赖无环，且每个依赖指向更早交付的变更。
- [ ] `roadmap.md` 有 MVP 切线声明，每个变更标了是否在切线内。
- [ ] 第一个变更是工程骨架 C0。
- [ ] 每个变更预计任务数 ≤ 12；超过的已经拆分。
- [ ] "状态"列没有由 agent 写入的内容。
- [ ] GR 检查一次或二次通过后，由负责人批准。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 依赖无环、每项 MVP 能力都有归属变更 | GR 检查失败并指出缺失项 |
| 第一个变更必须是工程骨架 | GR 失败，提示"先建工程骨架，后续变更才有基线" |
| 单个变更预计 ≤ 12 个任务 | GR 失败，要求拆分 |
| MVP 切线已标出 | GR 失败 |
| GR 是人工门 | `flow_submit` 通过后停在等待负责人，agent 无法自行放行 |
| 批准后 `project-clarify.md`/`roadmap.md` 冻结 | 写入被拒绝，提示走路线图增量 |
| 路线图"状态"列只有插件写 | agent 写入被拒绝 |
| C0 的 G2 允许 0 测试，G5 至少跑通 1 个测试 | 按门禁检查项判定 |

## 只做引导的部分

- 怎样按能力拆变更：粒度、合并与拆分、命名。
- MVP 切线画在哪、为什么这样画。
- 预计任务数怎么估、技术栈怎么选、部署方式怎么定。
- 项目级风险怎么看。

这些没有代码判定，靠你在 `project-clarify.md` 里写清理由，由负责人判断。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 一个变更包办整个项目 | 任务数一定超限，无法逐个验收，回滚成本高 | 按能力拆成多个变更，先交付最薄的一条链路 |
| 路线图只有变更名，没有验收要点 | 后续 S1 无据可依，验收标准只能临时编 | 每个变更为写 1–3 条可验证的验收要点 |
| 把功能排在工程骨架前面 | 没有测试框架和基线，后面所有验证都没有参照 | C0 第一，先立骨架 |
| MVP 切线写"以后再说" | 范围没有边界，工期不可控 | 明确列出切线外能力并写理由 |
| agent 自己改路线图"状态"列 | 状态是插件根据账本写的，手改会与事实冲突 | 只做交付，让插件更新 |
| 项目级澄清抄模板问题 | 问题与项目无关，负责人被迫答题 | 每个问题引用已读到的事实并说明会改变什么 |

## 正例

```markdown
# 路线图：会员管理系统
MVP 切线：C0–C3 在切线内；C4 在切线外（先手工导出应付，等有收入再做）。

| 变更 | 能力 | 一句话目标 | 验收要点 | 依赖 | 预计任务数 | MVP | 状态 |
|---|---|---|---|---|---|---|---|
| C0 | 工程骨架 | 能构建、能跑测试、有 CI | 测试框架跑通 1 个冒烟测试；CI 通过 | — | 4 | 是 | 未开始 |
| C1 | 用户与鉴权 | 手机号登录、区分会员与管理员 | 登录成功 / 失败 / 锁定三类场景 | C0 | 8 | 是 | 未开始 |
| C2 | 会员 | 开通、查询、到期提醒 | 开通后到期日正确；提醒按天触发 | C1 | 9 | 是 | 未开始 |
| C3 | 续费 | 支付回调、幂等、优惠叠加 | 重复回调只生效一次；到期日按规则推算 | C2 | 10 | 是 | 未开始 |
| C4 | 后台报表 | 会员与收入报表 | 导出 CSV 行数与口径一致 | C2 | 6 | 否 | 未开始 |
```

## 反例

```markdown
| 变更 | 能力 | 目标 | 依赖 | 状态 |
|---|---|---|---|---|
| C0 | 会员管理系统 | 做完整系统 | — | 进行中 |
```

问题：一个变更装了整个系统；没有验收要点；没有 MVP 切线；第一个变更不是工程骨架；agent 手写了状态列。GR 会在"第一个变更是工程骨架"和"单个变更 ≤ 12 任务"上直接失败。

## 与其他技能的衔接

- 批准后进入 `flow-clarify`（每个变更的 S1）。
- C0 的 G2/G5 特殊规则见 `flow-context`、`flow-verify`。
- 路线图增量同样由本技能处理，写完重新 `flow_submit({ gate: "GR" })`。
