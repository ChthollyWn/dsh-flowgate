# 学习卡：项目路线图（从 0 开发）

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

先做一次项目级澄清（目标用户、核心流程、MVP 边界、技术栈与部署、非功能要求、约束），再把项目按"能独立验收的能力"拆成若干变更写进 `.flowgate/roadmap.md`，标出 MVP 切线，最后让第一个变更固定是工程骨架 C0。这份路线图由负责人批准（GR）后冻结，后面每个变更从路线图条目立项。

## 为什么（why）

从 0 开发最容易犯的错是"一个变更装下整个项目"：任务数爆炸、没法逐个验收、出错只能整体回滚。路线图把大目标拆成可独立交付的能力，让每个变更都有清晰的验收边界；把工程骨架放在第一位，是为了在写业务前就拥有构建、测试和基线，否则后面所有"验证通过"都没有参照物。

## 合格标准（criteria）

- 项目级六要素都有结论或负责人接受的假设。
- 每个变更 = 一个能独立验收的能力，一句话目标与验收要点非空。
- 依赖无环，且都指向更早交付的变更。
- MVP 切线明确写出，每个变更标明是否在切线内。
- 第一个变更是工程骨架 C0。
- 每个变更预计 ≤ 12 个任务，超出的已拆分。
- 路线图"状态"列由插件维护。
- GR 由负责人批准。

## 对应上游做法（upstream）

- gstack 的 `/office-hours`、`/plan-ceo-review`：先问清目标与取舍，再审查计划是否值得做。
- Superpowers 的 brainstorming：先发散问题、再收敛成可执行方案。
- OpenSpec 的"一个能力一个 change"组织方式：把变更当作可独立归档的能力增量。

FlowGate 的改写：把"要不要做、先做什么"固化成可检查的路线图表格与 GR 人工门，让拆解结果可被代码检查（依赖、C0 位置、规模、MVP 归属），而不是只停留在讨论里。

## 常见反模式（antiPatterns）

- 一个变更包办整个项目，或路线图只有变更名没有验收要点。
- 把功能排在工程骨架之前，没有测试基线就开始写业务。
- MVP 切线写"以后再说"，范围没有边界。
- agent 手改路线图"状态"列，导致状态与账本不一致。
- 项目级澄清抄模板问题，不引用任何项目事实。

## 正例（good）

路线图分 C0 工程骨架 → C1 用户与鉴权 → C2 会员 → C3 续费，每行都有一句话目标、可验证的验收要点、依赖、预计任务数（均 ≤ 12）和 MVP 标记；C4 后台报表明确标为切线外并写了理由。GR 一次通过。

## 反例（bad）

路线图只有一行：`C0 | 会员管理系统 | 做完整系统 | — | 进行中`。没有验收要点、没有 MVP 切线、第一个变更不是工程骨架、状态由 agent 手写——GR 直接失败，返回缺失项与示例。
