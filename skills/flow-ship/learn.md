# 学习卡：S6 交付闭环

> 学习卡字段与 `LearningCard` 一一对应：做什么 / 为什么 / 合格标准 / 对应上游做法 / 常见反模式 / 正例 / 反例。

## 做什么（what）

G5 通过后进入 S6：逐项核对交付清单（任务、G5、场景证据、无未处理 critical/major、风险处理、篡改项、非 agent 改动），起草提交说明、PR 描述与 CHANGELOG，生成 HTML 交付报告和指标，提交 G6 并由负责人确认。之后插件把增量规格合并进主规格、把变更移入 `archive/`；推送与 PR 只在 G6 之后由负责人触发，分支合并方式由负责人选择。

## 为什么（why）

交付不是"代码合并了"。别人要能理解为什么改、改了什么、证据在哪、还有什么没做；出问题要能回滚到某个任务；规格要能沉淀为系统当前行为的描述。把交付清单变成 G6 的检查项，可以防止"带病发布"；把归档和推送交给插件与负责人，则保证了状态与账本一致、发布受控。

## 合格标准（criteria）

- 交付清单逐项确认。
- 场景证据齐全，手工证据已确认（高风险逐条）。
- 无未处理 critical/major；风险、篡改项、非 agent 改动有留痕。
- 提交按任务组织；PR 描述含需求、方案、证据、风险、未做事项；CHANGELOG 面向使用者。
- G6 由负责人批准。
- 归档由插件完成；推送/PR 在 G6 之后且经负责人触发。

## 对应上游做法（upstream）

- gstack 的 `/ship`、`/document-release`：交付时同步更新文档与说明，让变更可被接手。
- OpenSpec 的 archive：把增量规格合并进主规格，变更归档。
- Superpowers 的 finishing-a-development-branch：分支收尾方式（合并/压缩/保留）要有明确选择。

FlowGate 的改写：把"G6 人工门、推送受控、归档由插件执行、清单逐项检查"写进代码；把"PR 描述怎么写、分支怎么选"留作引导。

## 常见反模式（antiPatterns）

- G6 之前推送或开 PR。
- 交付清单靠"我检查过了"，没有逐项对照。
- 把多个任务压成一个提交。
- 跳过 CHANGELOG 或 PR 描述。
- 手动移动变更目录归档。
- 自己决定合并方式。
- 带着未处理 major 交付。

## 正例（good）

8 个任务全过、G5 无回归、5 个场景有证据（1 个手工证据待 G6 确认）、无 critical/major、风险与篡改项已处理、1 处非 agent 改动单列；PR 描述写清需求、方案、证据、风险与未做事项，CHANGELOG 写「新增：续费回调幂等与到期日计算」；G6 一次通过，插件归档并生成报告，负责人选择压缩合并后推送。

## 反例（bad）

G5 刚过就 `git push`（被拒）；手动移动变更目录到 archive（受保护路径，被拒）；PR 描述只有"完成了续费"；G6 被退回要求补齐场景证据与未做事项。交付被拖延，且本次没有留下可复用的记录。
