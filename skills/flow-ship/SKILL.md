# flow-ship：交付闭环（S6）

## 何时用

- S5 通过后进入 S6（G6 交付确认是人工门）。
- 负责人决定分支处理方式（合并、压缩合并、保留分支）时。
- G6 之后：推送、创建 PR、让负责人做最终确认。

## 产物路径

| 产物 | 路径 | 谁写 |
|---|---|---|
| 交付报告 | `.flowgate/changes/<id>/report.html` | 插件生成（`/flow report`） |
| 提交说明 / CHANGELOG | 仓库根 `CHANGELOG.md` 或项目指定文件 | agent 写（在允许阶段） |
| PR 描述 | 由你起草，负责人确认后手动或经批准推送 | agent 起草 |
| 归档 | `.flowgate/archive/<日期>-<change-id>/`、主规格 `.flowgate/specs/<capability>/spec.md` | 插件写 |
| 复盘 | `.flowgate/retro.md` | 插件写（下一步 `flow-retro`） |

## 步骤（照做即可）

1. **核对交付清单（G6）。** 逐项确认：
   - 全部任务完成并过了任务门；
   - G5 已通过；
   - 所有验收场景都有通过证据（自动化或经确认的手工证据）；
   - 没有未处理的 critical / major；
   - 风险项全部处理完毕（含单次放行、例外、豁免的留痕）；
   - 篡改检测项已确认；
   - 非 agent 改动已单列并确认。
2. **生成交付物。** 起草：
   - 提交说明：按任务组织，一条提交对应一个任务（插件会按任务自动提交 `flowgate(<变更>/<任务>): <标题>`，不要重排或改写历史）；
   - PR 描述：需求摘要（做 / 不做）、方案与关键决定、证据（测试与运行证据链接）、风险与处理、未做事项；
   - CHANGELOG 条目：面向使用者写"新增 / 修复 / 变更"，不要贴实现细节。
3. **生成报告与指标。** `/flow report` 生成单文件 HTML 报告（概览、需求、计划、执行、验证、风险、指标、附录）；`/flow metrics` 查看本次 M-1～M-18。报告默认在 `.flowgate/` 内，要进 PR 时再复制出来。
4. **提交 G6。** 调用 `flow_submit({ gate: "G6" })`；失败的检查项按 `failures[].hint` 逐条补齐。通过后等待负责人：`/flow approve G6` 或面板确认。
5. **G6 之后归档（插件执行）。**
   - 增量规格合并进 `.flowgate/specs/<capability>/spec.md` 主规格；
   - 变更目录移入 `.flowgate/archive/<YYYY-MM-DD>-<change-id>/`；
   - 路线图对应条目状态更新；变更冻结契约结束。
6. **分支处理。** 负责人选择合并、压缩合并或保留分支（借鉴 finishing-a-development-branch 的做法）。选择前把交付报告打开给负责人看；不要自行决定合并方式。
7. **推送受控。** `git push`、创建 PR 只能在 G6 之后、由负责人触发或明确确认。G6 之前推送会被拒绝。
8. **建议开新会话。** 一个变更一个会话；归档后状态条会提示开新会话，只带 `project.md`、`roadmap.md`（如有）、相关主规格和最新交接摘要。
9. **转入复盘。** 交付完成后用 `flow-retro` 解读指标、提议规则沉淀。

## 合格标准（可对照检查）

- [ ] 交付清单逐项确认，没有"应该没问题"。
- [ ] 验收场景证据齐全，手工证据已经负责人确认（高风险逐条）。
- [ ] critical / major 全部处理（修复或书面豁免）。
- [ ] 风险项、篡改项、非 agent 改动都有留痕。
- [ ] 提交说明按任务组织，没有压成一个大提交。
- [ ] PR 描述包含需求、方案、证据、风险、未做事项。
- [ ] CHANGELOG 条目面向使用者。
- [ ] G6 由负责人批准。
- [ ] 归档由插件完成，没有手动移动目录。
- [ ] 推送与 PR 在 G6 之后且经负责人触发。

## 代码会强制的部分

| 检查 | 不满足时 |
|---|---|
| 交付清单全部满足 | G6 检查失败，列出缺失项 |
| G5 通过、任务全部完成 | 不能进入 G6 |
| 验收场景证据齐全；手工证据经负责人确认 | G6 失败或要求逐条确认 |
| G6 是人工门 | `flow_submit` 通过后停在等待负责人，agent 不能自行放行 |
| 归档由插件写 | agent 移动/删除变更目录会被拒绝 |
| 推送与 PR 受控 | G6 之前 `git push` / 创建 PR 被拒绝；过后转人工确认 |
| 变更分支与自动提交 | S4 进入时建分支、每个任务过门自动提交，agent 不要重写历史 |
| 报告与指标由插件生成 | `report.html`、`metrics/` 是插件写，agent 不能伪造 |

## 只做引导的部分

- PR 描述怎么写让审阅者快速理解。
- 提交说明与 CHANGELOG 的措辞与粒度。
- 分支合并方式的选择依据。
- 哪些"未做事项"值得写进 PR（比隐藏更有用）。

## 常见反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| G6 之前就推送/开 PR | 受控规则拒绝，且可能把未确认变更推出去 | 等 G6 批准后由负责人触发 |
| 交付清单靠"我检查过了" | 没有逐项对照，G6 会失败 | 按清单逐条核对并留痕 |
| 把多个任务压成一个提交 | 无法按任务回滚，审查与报告对不上 | 保留插件按任务生成的提交 |
| 跳过 CHANGELOG / PR 描述 | 别人无法接手，也不利于回滚 | 按使用者视角写清 |
| 手动把变更目录移到 archive | 受保护文件，状态会与账本不一致 | 让插件归档 |
| 自己决定合并方式 | 分支策略是负责人的决定 | 给报告，让负责人选 |
| 带着未处理 major 交付 | 会进入报告与后续维护成本 | 修复或申请书面豁免 |

## 正例

G5 通过后，agent 逐项核对交付清单：8 个任务全部通过、G5 无回归、5 个场景有证据（其中 1 个手工证据已标黄待确认）、无 critical/major、2 条风险已处理、1 处非 agent 改动已单列。生成 PR 描述（需求摘要、方案、证据链接、风险、未做事项）和 CHANGELOG「新增：续费回调幂等与到期日计算」。`flow_submit G6` 通过后负责人批准；插件归档并用 `/flow report` 生成报告；负责人选择压缩合并后手动推送。

## 反例

agent 在 G5 刚过就 `git push`，被拒后才想起 G6；它手动把 `.flowgate/changes/C-003` 移到 archive（受保护路径，写入被拒）；PR 描述只有一句"完成了续费"，没有证据与风险；G6 被退回要求补齐场景证据与未做事项。

## 与其他技能的衔接

- 前置：`flow-verify`、`flow-review`、`flow-qa`。
- 后续：`flow-retro` 做复盘与规则沉淀。
- 从 0 开发时，交付后更新 `roadmap.md` 状态并开始下一个变更。
